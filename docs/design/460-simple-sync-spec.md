# 溜狗同步簡化規格

狀態：2026-10-23 K 確認先簡化同步流程，再處理人工改表 GAS；依此順序與驗收範圍發布規格，標記 ready-for-agent。尚未實作、部署或啟用。

已發布：[#498](https://github.com/jiatsenK/bq-shelter-dogs/issues/498)。

## Problem Statement

志工在網站登記「溜了」或復原時等待很久，難以判斷是否收到操作；11 隻常溜狗整群登記已在本機重現被舊入口拒絕。同步責任又混在一起：寫回重試會先掃表，正常派送與重試有重複流程，人工改表通知未送達時沒有完整補送保障。這增加資料庫操作與維護負擔，也讓現場志工不確定網站與試算表哪個可信。

本規格承接 #441、#460 與 PR #487，修訂 PR #439 所提出的 ADR 0017 相關設計；不另外重做已完成的 D1 基礎功能。優先簡化責任與流程，CPU 數字作為後續驗收，不以降頻或提高預算冒充單次成本改善。

## Solution

保留三個原則：D1 保存最新已接受狀態；網站操作接受後背景寫回試算表，失敗或結果未知才補處理；人工改表立即通知網站同步，保險掃描只補漏。

志工按下操作立即看見處理中，D1 接受後畫面更新，不等待試算表。整群可跨內部批次完成，逐狗呈現結果。人工通知送不出去時由 GAS 保存待通知版本並自動補送；完全沒有觸發的修改，由每日台灣時間 09:43、13:53、23:53 的保險掃描補回。

## User Stories

1. 身為志工，我希望各頁看到同一份 D1 最新狀態，避免不同入口互相矛盾。
2. 身為志工，我希望按「溜了」立即看到處理中，知道網站已收到操作。
3. 身為志工，我希望復原也立即有回饋，避免因等待而重複按下。
4. 身為志工，我希望 D1 接受後立即看到結果，不受試算表回應速度拖累。
5. 身為志工，我希望尚未接受或結果未知時不顯示成功，避免誤判。
6. 身為志工，我希望試算表寫回失敗時自動重試，不必重新登記。
7. 身為志工，我希望清楚區別登記成功與試算表尚未同步，知道是否需要操作。
8. 身為志工，我希望 11 隻常溜狗可以整群登記，不必自己拆群。
9. 身為志工，我希望群組跨內部批次時仍逐狗顯示結果，知道哪些已成功。
10. 身為志工，我希望部分失敗只重試未確認的狗，不重複登記已成功者。
11. 身為志工，我希望斷線後重送同一操作不重複生效，能放心恢復使用。
12. 身為志工，我希望另一支手機依既有更新節奏看到 D1 結果，減少現場混淆。
13. 身為志工，我希望人工輸入、貼上多格、刪名、清空及改日期都能同步到網站。
14. 身為志工，我希望人工刪除的名字不被舊工作重新加回，保留有效修正。
15. 身為志工，我希望多人同狗同日登記保留有效名單，不互相覆蓋。
16. 身為志工，我希望復原沿用既有權限、日期與衝突規則，不誤取消別人的新修改。
17. 身為志工，我希望昨日延遲工作不覆蓋今日新登記，跨日仍顯示正確結果。
18. 身為維護者，我希望改表通知暫時失敗會自動補送，不需逐次手動補救。
19. 身為維護者，我希望舊通知成功時不清掉更新的修改，避免遺漏。
20. 身為維護者，我希望 Worker 接手後未完成的比對能繼續，不必等下一次全表掃描。
21. 身為維護者，我希望完全漏觸發仍有固定補漏時段，並清楚知道等待限制。
22. 身為維護者，我希望寫回重試只處理未完成工作，不因一隻失敗反覆掃整張表。
23. 身為維護者，我希望單狗、多狗、初次派送與重試共用核心，減少重複維護。
24. 身為維護者，我希望預算拒絕、版本衝突與遠端故障可分辨，不被通用重試掩蓋。
25. 身為維護者，我希望先驗證真實人工編輯能抵達另一支手機，再降低保險掃描頻率。
26. 身為維護者，我希望成本與未完成工作可追查，且失敗不丟棄已接受的登記。

## Implementation Decisions

- **階段一先完成同步流程簡化。** 寫回重試與掃描分離，單狗、多狗與重試共用派送核心；以 11 隻整群登記、逐狗結果，以及登記／復原在 D1 接受後不等試算表的畫面回饋作驗收。優先承接 #460／PR #487，不先擴大成人工通知改造。
- **階段二再處理人工改表 GAS。** 階段一完成後，實作與確認人工觸發、持久待通知版本、失敗補送及 Worker 未完成比對恢復。取得部署／設定授權後完成真實人工編輯到另一支手機的驗收，通過才啟用每日三次保險掃描。階段一不得提前降低正式掃描頻率；功能開關仍維持關閉，啟用另行授權。
- D1 接受狀態與待寫回工作維持原子提交；保留請求識別、單調版本與資料包的一致性。手機只在 D1 接受後反映成功；舊快照及逆序回應不得降版。
- 將工作分成三個清楚入口：網站接受後背景派送；人工通知後比對並接納人工修改；定期保險掃描補漏。寫回重試不先掃表，人工通知比對不順便派送無關工作。衝突處理仍可依既有協定直接讀取相關資料。
- 單狗與多狗、背景派送與重試共用一個派送核心，集中認領、版本核對、預算檢查、結果確認與收尾。批量只是內部執行方式，不成為群組大小限制。
- 區分預算拒絕、版本競爭與遠端失敗；不能把任何錯誤都退回逐狗重跑，也不能僅提高預算掩蓋問題。保留差異寫入與共用寫入預算，納入資料包、索引及觸發器成本。
- 不先整併資料表或刪除基準、回執等併發證據；保留可信讀回、舊派送失效及未知結果恢復。逾時不表示 Google 沒有寫入，不直接重放舊整格值。
- 保留 ADR 0017 方案 A：直接手改仍開放，寫前核對、衝突停止並重新比對；已接受最後核對到寫入之間的人工競爭限制。不得以簡化為由忽略已觀測到的刪名、清空或日期修正。
- GAS 人工值修改使用已授權的安裝型編輯觸發器；結構變更另行處理，避免 EDIT 重複通知。程式或 API 寫入不可假定會觸發人工編輯通知。
- GAS 用單一持久待通知版本合併修改，由一個固定時間觸發器補送。缺設定、HTTP 失敗或結果不明保留待通知；Worker 必須持久接手才確認收到。確認只清除同一版本，更新版本不得被舊確認清除。
- GAS 鎖只保護短暫標記操作，不跨通知 HTTP 等待持鎖，避免 Worker 回呼 GAS 時互等。補送有界，沿用可恢復的未完成狀態，不新增逐事件佇列。
- Worker 沿用持久 pending；比對有剩餘、分批未完成或結果不明時保留並及時繼續，不能提早標記 idle。通知補送及未完成工作恢復不等每日三掃。
- 保險掃描目標時段為台灣時間 09:43、13:53、23:53，與寫回重試分開。完全漏觸發可能接近十小時才被發現，另加處理時間；掃描故障可能更久。這是已接受的補漏限制，不是所有變更的即時保證。
- 整群至少支援已回報的 11 隻與跨內部批次情境，逐狗顯示接受結果。未知結果沿用請求識別查明或安全重試，不為已成功的狗建立新操作。
- 操作回饋沿用既有狀態呈現：處理中、D1 已接受、試算表同步中／尚未同步、可辨識失敗；不新增等待試算表才更新的關卡。另一手機保留前景每分鐘、回前景超過 30 秒重讀與背景暫停規則。
- 實作同步修訂 ADR 0017 與相關名詞、設計及啟用說明，區分目前關閉功能與啟用後契約。非今日資料同步、既有歷史與 ADR 0006 寫表範圍保持原責任。

## Testing Decisions

- 主測試邊界採既有網站操作／Worker 公開入口：從登記、復原、通知或排程輸入，驗證可見狀態、持久接受與試算表結果；不以私有函式、資料表拆法或精確 SQL 次數作為產品正確性的契約。
- 沿用現有登記、群組、D1 入口的前端整合測試，以及 Worker 接受、寫回、重試、比對測試與既有 D1 測試資料。優先擴充既有接縫，不新增一套平行測試框架。
- 測試登記與復原按下後、伺服器回應前即有處理中；刻意延遲或拒絕試算表回應，確認 D1 接受後畫面已更新，未接受時不假報成功。
- 測試 11 隻及跨批次群組、部分成功、斷線未知結果與重試，驗證逐狗結果及不重複生效。
- 測試多人登記、刪名、清空、日期改早、跨裝置復原、午夜、新舊版本交錯、晚到回執與未知寫回，不讓舊工作覆蓋有效新狀態。
- 在外部服務邊界模擬通知 HTTP 錯誤、缺設定、回應遺失、重複通知、新修改與舊確認交錯及程序重啟；驗證待通知版本、Worker 持久接手與後續恢復。GAS 標記／觸發入口只補必要的服務邊界測試。
- 測試未完成比對超過單輪容量仍繼續；重試入口不做無關全表掃描，無待處理工作不派送，無差異不重寫業務資料。驗證三個補漏時段的台灣時間換算。
- 本機測試一律經統一 check-local 入口並提供原因；已知四項既有 local-check 測試失敗單獨列出，不歸因於本變更。
- 正式環境驗收另列：取得部署／設定授權後，由志工帳號實際輸入、貼上多格、刪名、清空與改日期，核對 GAS 執行、Worker 接受、D1 新版本及另一支手機。手動呼叫通知或 HTTP 成功不能取代這項驗收；通過前不啟用每日三掃。
- 成本驗收先做本機差異預演與代表工作量比較，分開列出掃描、派送、回呼與重試；本機時間不冒充線上 CPU。線上 CPU 驗收需另獲授權，保留 10 ms 門檻，不把較少掃描次數當成單次達標。

## Out of Scope

- 本規格發布不包含程式實作、正式部署、GAS 觸發器安裝、資料遷移或功能開關啟用。
- 不新增事件佇列、SSE、WebSocket、Durable Object 或試算表控制欄；不重做資料表架構。
- 不改非今日資料同步、歷史展示、志工身分或復原權限；沿用 #441／#460 已確認約束。
- 不單獨修補舊入口後就宣稱簡化完成；11 隻故障與操作回饋納入新流程驗收。
- 不執行線上 cpu-bench、不加觸發該工作流程的標籤，也不追查本次改動前既有的四項 local-check 測試失敗。
