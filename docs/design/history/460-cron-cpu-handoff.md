## 目前進度（2026-10-22，K 確認架構簡化）

- K 要求先簡化同步架構。三個核心原則：D1 是最新狀態主要來源；網站登記後背景寫回，失敗或未確認才重試；人工改表通知立即同步，定期掃描只補漏。
- 定期補漏每天三次，全部為台灣時間：**09:43、13:53、23:53**。避開志工工作時段 10:00–12:00、14:00–16:00。這取代先前「每 10 分鐘保險掃描」的設計；目前尚未修改正式排程。
- 寫回重試與全表掃描拆開：補送只處理未完成工作，不先掃表；人工通知只收人工修改，不順便派送。通知失敗與寫回失敗的重試不等每天三次掃描。
- 正常派送與重試共用實作，單狗／多狗不各維護一套認領與收尾；集中管理工作版本、派送識別、重試資訊。保留版本核對、可信讀回與未知結果處理，避免舊工作蓋掉新登記。
- Codex 靜態檢查發現：`dispatchWalks` 的十隻工作保留量為 `96 * 10 = 960`，超過 `writeBudget` 預設單次上限 500；測速設定未覆寫此上限，通用 catch 會退回逐隻派送。因此先前結果不能當作合併派送成功執行後的效能證據。尚未以本機測試驗證，也沒有新的 CPU 分段量測。
- 下一步實作須區分預算拒絕、版本競爭與遠端失敗；不能將所有錯誤都轉成逐隻重跑，也不能只提高預算門檻來掩蓋問題。
- 本次只更新設計與交接。`SITE.d1WalkAccept` 維持關閉，Apps Script 未部署，不觸發線上 cpu-bench。

### 降低掃描頻率前的必要驗收（K 補充）

研究結果見 [簡化寫回責任與人工改表通知](../../research/2026-10-22-460-simple-sync-and-notification.md)。內容是建議，尚未實作。Google change 事件也包含 EDIT，因此不能由目前採「變更時」直接斷言人工輸入不會觸發；仍須查正式安裝及實測。另須修正掃描 `deferred` 可能被標成 idle 的缺口。

- 必須確認志工實際在試算表輸入會觸發 GAS，並一路更新到 D1 與另一支手機；不能以手動執行 `notifyWorker` 或只有 HTTP 成功代替驗收。
- 人工值修改使用已授權的安裝型「編輯時」觸發器；結構變更的「變更時」另行處理並避免重複通知。驗收涵蓋輸入、貼上多格、刪名、清空及改日期。
- 現況只查到 repo 的安裝說明使用「變更時」，無法從 repo 確認正式 GAS 觸發器是否安裝、授權或成功執行。官方依據：https://developers.google.com/apps-script/guides/triggers/installable 。
- `notifyWorker` 缺 URL／金鑰時直接返回，HTTP 錯誤被 `muteHttpExceptions` 接住後未檢查，也沒有 GAS 端持久補送。Worker 端 pending 只能補已抵達的通知，無法補根本沒送達的通知。實作時須明確處理這個缺口，不能宣稱目前通知失敗已有完整重試。
- 正式驗收須在部署與設定授權後，由志工帳號實際編輯，核對 GAS 執行紀錄、Worker 接受結果、D1 新版本及手機顯示。通過前不將每日三次掃描當成已可安全啟用。
