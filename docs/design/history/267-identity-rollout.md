## 資料結構與相容方式

- `v3_volunteers.volunteer_id` 保留既有有效身分；`v3_identity_names` 保存名字正規化、原名與代號，合併時把對照指向目標身分。
- `v3_identity_redirects` 保存已合併身分，所有轉向直接指向有效目標，不形成多層循環。退役志工列以內部名稱讓出 UNIQUE name；舊名字保存在名字對照，推薦名單不列退役身分。
- `v3_volunteer_favorites`、`v3_volunteer_cards` 只以固定志工與永久狗 ID 持有資料。舊 `v3_favorites` 空表及 `v3_card_opened` 保留為來源；不 DROP、不清表、不把舊代號當成新資料擁有者。
- 首次建立確定名字對照時，原代號資料取最早日期接回身分；已接過的對照不重搬，避免取消的收藏復活。未知代號留在原表，待取得確定名字後接回。
- 更名、合併與編輯紀錄在同一個 D1 batch；全域 revision guard 防止確認期間任何身分／收藏／開卡／歷史變動後仍套用舊確認。原始溜狗列與當時名字／代號不改寫。
- 個人 API 保留舊 `codes` 參數，但先解析到固定身分。新版前端個人資料請求只送一個代號；全部名字代號只用來比對歷史。未設定名字仍在手機收藏。

## 演練接縫

`scripts/migrate-volunteer-identity.mjs` 不自行連外：

- `inspectVolunteerIdentity(db, codeFor)` 只讀取呼叫者提供的 DB。`codeFor(name)` 必須使用原本的 WALKER_KEY 算法，可由既有服務已核對的名字對照提供。回傳 confirmed、conflicts、unknownCodes 及每種資料的 total／confirmed／pending；含個資的詳細內容不得提交 Git。
- `migrateVolunteerIdentity(db, keyOrCodeFor)` 接受原 WALKER_KEY，或從原服務已核對的 codeFor(name)，不更換算法。在結構準備好後，逐一接回確定名字並核對既有 ID；可重跑，遇正規化歧義即停止，不自行合併。傳入正式綁定即會寫正式資料，須另行確認。
- 本機 `worker/test/identity.test.mjs` 使用 SQLite 與公開 Worker API 驗證重跑、未知代號保留、取消不復活、同時設定名字、更名／合併失敗回復、最早開卡日及歷史不變。完整正式快照的隔離演練結果另見上方證據，不以假資料代替。
