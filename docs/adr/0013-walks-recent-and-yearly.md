# 0013 網站只拿近期溜狗紀錄，舊的按年拿，「我溜過的狗」由 Worker 彙總

日期：2026-10-17（K 決定，#341）

## 背景

`/api/walks` 每次回傳全部溜狗紀錄。D1 讀取量已經由 ADR 0009 的資料包解決（新機器約 47 列），但回應大小和 Worker CPU 會跟著歷史一直變大：20 年容量原型（`prototype/capacity-20y`，`docs/research/2026-10-17-capacity-20y.md`）量到 1 年後約 1.5 MB、20 年後約 30 MB；組回應的 CPU 在本機 1 年後 32 ms、20 年後 699 ms，免費方案每次請求只有 10 ms。手機每開一次頁面都要下載這一份。

逐頁查過，真的需要完整歷史的只有板收圖鑑的「我溜過的狗」（`cards.js` 的 `bqMyDogs`：溜過一次就拿得到卡，要算幾天、第一次、最近一次）。其他頁面都只看最近一兩個月。

## 決定

- **`/api/walks` 只回近期溜狗紀錄**：上個月 1 號到今天（最長約 62 天）。桌面看板的 30 天、圖鑑的「這個月幾次」、我溜過月曆的預設畫面都夠用。回應約 100～150 KB，不隨年數變大。
- **更舊的按年拿**：`/api/walks?year=YYYY`，直接用 Worker 已有的一年一份資料包。網址帶那一年的版本號，回應加 `Cache-Control: immutable`，手機下載過就不再拿。只有我溜過月曆往前翻到更早的月份才會用到。
- **「我溜過的狗」由 Worker 彙總**：重算每年資料包時，順便存一份年度摘要「每個代號對每隻狗：溜過幾天、第一次、最近一次」（照「同一隻狗同一天以最後一筆為準」）。新增 `POST /api/walks/mine`，代號放在請求內容（不放網址），Worker 把各年摘要和切點以後的紀錄加總後回傳。每次約讀 20 列，回應只有這個人溜過的狗。代號清單本來就含舊代號，換名字、合併身分（0005）照用。
- **分析頁的月統計拿掉**（這個月每天幾次、和上個月比）。K 不需要。
- **單隻狗的歷史只用近期溜狗紀錄算**：最近 30 天的格子不變；「平均隔幾天、最久隔幾天」只算近期範圍，超出範圍顯示「超過 62 天」。
- **直接換**：不保留回傳全部歷史的入口。網站沒有離線版，重新整理就是新版。

## 沒選的做法

- **按月分段拿**：每段比較小，但請求數多；Worker 的資料包本來就一年一份。
- **手機在 IndexedDB 存完整歷史**：要自己管版本和清除；換手機就不見，違反 0001（志工資料跟著代號走）。
- **請求時用 SQL 彙總（`GROUP BY`）**：D1 照掃過的列計費，20 年後每次約 40 萬列（`docs/research/2026-10-17-monthly-stats-cost.md`）。
- **依代號查 D1（`walker_code` 索引）**：「同一天以最後一筆為準」要同一天其他人的列，查詢複雜；資深志工每次幾千列。
- **Cache API**：只存在當地資料中心，官方沒保證 workers.dev 能用。改用瀏覽器快取。
- **單隻狗歷史另開 API 查全部日期**：要多一支 API，每次約讀 3,000 列；超過兩個月的間隔對「最近有沒有被冷落」幫助不大。

## 後果

- `/api/walks` 的回應大小和 CPU 不隨歷史變大；「我溜過的狗」每次約 20 列。
- 年度摘要跟著資料包的月份版本號重算，舊紀錄被改時一起更新，不另外寫觸發器。
- 單隻狗「最久隔幾天」最多只能說到「超過 62 天」。
- 前端要改：`app.js`（我溜過月曆往前翻）、`cards.js`（我溜過的狗改讀 `/api/walks/mine`）、`analysis.js`（拿掉月統計、單隻狗歷史）、`desk.js`（不用改，30 天在範圍內）。
