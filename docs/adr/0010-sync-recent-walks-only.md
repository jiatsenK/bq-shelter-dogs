# 0010 同步只比對最近一段溜狗紀錄，舊紀錄定下來

日期：2026-10-16（K 決定）

取代 ADR 0009「另開票、還沒做」裡的「同步只讀變動部分」那段（包括「保險同步保留整份比對」）。

## 背景

同步每次 `SELECT * FROM v3_walks` 讀整張表（`scripts/sync-compact-d1.mjs`），寫回時也整張刪掉重寫。現在一次約 1,200 列、一天約 50 次；三年後一次 4.5 萬～12 萬列，一天約 230 萬列，是 D1 最大的讀取來源（研究：PR #327 的 `docs/research/2026-10-16-d1-table-audit.md`）。

試算表每隻狗只有「最後一次溜狗」（約 118 列），沒有歷史可以拿來比對。D1 的歷史是同步一筆一筆累積起來的。整張讀的原因是程式整張重寫，不是真的需要比對。

## 決定

- **昨天以前的溜狗紀錄定下來**：K 說「過去的只是數值」，大家本來就是看這一張表，沒有人會回頭改舊紀錄。試算表上舊日期就算被改掉，同步也不理；真的要修正，走網站的編輯紀錄（0004）。
- **平常的同步只比對最近一段**：從「上一次成功同步的前一天」到今天，用 `v3_walks_date` 索引讀；寫入也只動這一段，不再整張刪掉重寫。正常情況下就是昨天和今天。起點用上一次成功同步，因為同步可能停擺（例如 GitHub Actions 分鐘數用完，#329），停擺後第一次同步會自動補回。
- **6:30 保險同步（0008）保留，但不做全量**：除了上面那一段，再用主鍵（狗＋日期）逐一核對試算表上每隻狗的最後一次溜狗，有缺就補。一次約讀 118～240 列，只跟狗的數量有關，不隨歷史變多。
- **全量核對改成人工觸發**：同步 workflow 加一個選項，勾了才讀整張表比對。平常不跑。
- **D1 自己有沒有被改（例如網站編輯舊紀錄）**：由 #320 的每月版本號負責，同步不另外檢查，也不讀資料包。

## 沒選的做法

- **同步改讀 walks 資料包**：同步會依賴網站用的資料包格式和版本號；資料包過期或格式改了，同步就跟著錯，今天的紀錄也還是要另外讀。
- **固定天數（例如 60 天）**：同步停擺比天數還久就會漏；沒停擺時又多讀很多。
- **每天整份比對當核對**：試算表上沒有舊資料，比不出東西；三年後一天至少多讀 4.5 萬列。

## 後果

- 同步讀取量不隨歷史總量成長：平常一次幾十列，6:30 約 240 列。
- 試算表上改舊日期不會反映到網站（刻意的）。
- 同步要記下「上一次成功同步」是哪一天（放在 `v3_sync_state`）。
