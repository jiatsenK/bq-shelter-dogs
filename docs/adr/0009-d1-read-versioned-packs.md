# 0009 減少 D1 讀取：版本號＋資料包＋只讀今天

日期：2026-10-16（K 決定）

## 背景

正式 D1 一天讀約 110 萬列（Cloudflare 主控台，約 24 小時）。最大來源是 `/api/walks`：一天約 200 次，每次讀約 2,400 列（溜狗紀錄約 1,200 列，SQL 排序讓讀取量加倍）。同步每次讀整表。`/api/today` 目前讀 0 列，因為正式 D1 還沒有 `v3_today_walks`；表一建好，手機每分鐘抓一次，估計一台每天約讀 18 萬列。

原型（分支 `prototype/d1-read-reduction`，研究筆記 `docs/research/2026-10-16-d1-read-prototype.md`）實測：歷史資料包＋只讀今天＋記憶體快取，4 支 API 輸出和現在逐字元相同；用正式的量重算，一天約 8 萬列，約現在的 7%。

## 決定

- **版本號**：分 `small`（狗清單、離所、休養等）、`walks`（今天以前的溜狗紀錄）、`live`（今天的溜狗紀錄）、`today`（`v3_today_walks`）四個，全部由 D1 觸發器在新增、修改、刪除時自動加 1，不靠各寫入路徑自己記得。`v3_walks` 依日期決定動 `walks` 還是 `live`，今天新增一筆不會讓歷史資料包重算。
- **資料包**：`small` 和 `walks` 算好存進 D1；Worker 每次只讀 1 列版本號，有變才讀資料包或重算。今天的紀錄另外即時讀（只讀今天的列）。
- **`/api/today` 最先做**：拆成單獨一張票，在正式 D1 建 `v3_today_walks` 之前上線。每次只讀 1 列 `today` 版本號，有變才重讀今天的列。`/api/today` 仍只是同步前的暫時消息（0007），手機照舊和狗清單資料、自己的紀錄合併。
- **取代 0007 的 15 秒快取**：Worker 記憶體快取改成看版本號；按溜了／復原時不用再手動清快取（觸發器會改版本號，所有 Worker 機器都看得到）。
- **一起修的地方**：不用 SQL 排序，讀出來在 Worker 裡排；加 `walk_date` 索引；狀態頁不再整表 `COUNT(*)`。
- **資料包一律分段存**：每段最多 1 MB，變大時自動多一段。D1 一列上限 2 MB，現在約 187 KB，約 2 年後會超過；一律分段讓這條路從第一天就在跑、就有測試。
- **其他手機看到修改**：改介紹或休養後，改的那台手機馬上看到，其他手機最慢 1 分鐘看到。
- **順序**：`/api/today` → ①歷史資料包＋只讀今天 → ②同步只讀變動部分。

- **溜狗歷史按月分段（K 2026-10-16 追加）**：walks 資料包改成一個月一包，每包有自己的版本號，觸發器依 `walk_date` 的月份只讓那一包失效；跨日只把昨天補進當月那包，不再整份重讀。讀取量不隨歷史總量成長（跨日約 110 列、改舊紀錄只重算那個月約 3,300 列）。存法用「按月失效、按年存成少數大列」（K 2026-10-16 看原型數字後決定，做法 B）：D1 照掃過的列數計費、跟一列多大無關，所以每月版本號放在版本號那一列的 JSON 裡（觸發器用 `json_set` 加 1），資料包一年一份、切成每段最多 1 MB 的大列；改舊紀錄只重算那個月，再把那一年的大列寫回。3 年資料實測：新開的 Worker 機器 18 列（一月一列是 151 列）、改舊紀錄約 5,000 列、跨日多寫約 4～14 列。依據 `docs/research/2026-10-16-d1-pack-growth.md`、原型 `prototype/d1-monthly-packs` 的 `docs/research/2026-10-16-d1-monthly-prototype.md`。

- **溜狗日期包（K 2026-10-27 追加，#679）**：狗清單的溜狗日期（`walkedDate`）和溜狗人（`walkers`）拆成另一個溜狗日期包，版本號是 `v3_pack_versions.walked`，跟 `small` 同一列，沒變時仍只讀 1 列版本號。試算表送「溜過了」只改這兩欄，只讓 `walked` 加 1、只重算溜狗日期包（只讀主清單 1 張表）；`small` 只在狗的資料真的變動時失效。溜狗日期包照主清單順序存編號、狗名，所以主清單加、刪狗或改列號、編號、狗名時兩個版本號都加 1。Worker 讀狗清單時把溜狗日期包蓋回在所資料包，輸出跟直接讀表相同；網站不用改。
- **同一台機器共用重算（K 2026-10-27 追加，#679）**：同一個版本號正在重算時，同一台 Worker 機器後進來的請求等同一次的結果；等的那次失敗就自己再算。只在同一台機器有效，不保證全域只算一次。不做 Durable Object：多一層呼叫和計費，D1 裡的資料包本來就是跨機器共用的快取。

## 另開票、還沒做

- **同步只讀變動部分**（已由 ADR 0010 取代：舊紀錄定下來，保險同步不再整份比對）：試算表每隻狗只有最後一次溜狗，一次同步最多動約 118 列紀錄，改成照主鍵只讀這些列；補代號、找「我最後一次溜」改走索引；每天早上的保險同步（0008）保留整份比對當核對。粗估讀取再降到約 3%（未實測）。不在 0008 的範圍。
- **`synced_at`**：同步每次寫主清單第 0 列的 `synced_at`（`worker/src/compact.js` 讀它），會讓 `small` 資料包每次同步都失效。放在上面那張票一起改；在那之前每次同步多重算一次（約 705 列），可接受。

## 沒選的做法

- **統計在後端先算好**（每隻狗最後散步日、志工月曆、本月統計等）：省的主要是手機下載和前端運算，不是 D1 讀取，又要改 API 格式和前端。先不做。
- **版本號變了只讀新增的那幾筆**：改紀錄、刪紀錄、跨日都要另外處理；今天的列只有幾十筆，整份重讀就好。
- **資料包超過門檻才切換成分段**：切換那段程式約 2 年後才第一次跑，壞了沒人發現。

## 後果

- D1 讀取預估降到約現在的 7%，同步那張票做完約 3%。
- 其他手機看到改介紹／休養，從馬上變成最慢 1 分鐘。
- 觸發器每改一列多寫 1 列（D1 寫入額度一天 10 萬列，影響小）。
- 新增版本號、資料包的表與觸發器，寫進 `db/compact-schema.sql`。
