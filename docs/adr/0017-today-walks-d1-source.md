# 0017 今日溜狗以 D1 為準，Worker 寫回試算表

狀態：**草稿，等 K 確認**（2026-10-20）。確認後才實作。修訂 0007、0012，補充 0008。

## 背景

今日溜狗資料散在試算表、D1、Worker 快取、手機 localStorage 四處，各有各的「以誰為準」，造成不同步與名字錯置（#435、#438）。研究見 `docs/research/2026-10-20-d1-single-source-sync.md`、`docs/research/2026-10-20-sheet-editors-in-d1-sync.md`。

ADR 0012 當初不讓 Worker 自己同步，是因為整份同步 CPU 要 64–152 ms，超過免費方案每次 10 ms。這次只讀主清單「犬名／編號／誰遛的／日期」並和 D1 比差異，實測見 `docs/research/2026-10-20-sheet-diff-cpu.md`：熱的 1–4 ms，isolate 第一次跑約 10–16 ms（貼近上限），所以要把讀進來的欄位縮到只剩需要的幾欄。

## 決定（K 已決定）

- **今日溜狗以 D1 為準**：「今天誰溜了哪隻」只有一份正本在 D1，網站、手機都讀 D1。取代 0007「試算表是正本」。
- **寫入順序**：網站按溜了／復原，先寫 D1，再由 Worker 寫回試算表（寫入範圍照 0006，不變）。取代 0007「寫試算表成功後才記 D1」。
- **寫回失敗**：D1 那筆標「待寫回」，由 Cron 重試；按的人不用等、不用重按。
- **偵測試算表手改**：沿用現有 Apps Script onChange 觸發器（`apps-script/sheet-write.gs` 的 notifyWorker → Worker `/sheet-changed`），但改成**收到通知立刻讀主清單比對**，不再只記「有改」等下一格。Cron 當保險，定期再比一次（觸發器會漏掉排序、部分貼上）。修訂 0012。
- **Cron 頻率**：在免費方案額度內即可（Workers 請求、D1 讀寫、CPU 都不超過），實作時依實測挑定。
- **寬限期**：網站剛寫、還沒寫回或試算表還讀到舊值時，D1 的名字先保留一段時間不被比對蓋掉；長度依上線後實測效能（寫回與 gviz 延遲）再定。
- **兩人同溜同一隻**：沿用「甲、乙」名字聯集。
- **手動刪名、清空**：尊重試算表（寬限期過後），D1 跟著刪。
- **試算表不加保護**：不加資料驗證、保護範圍（0006 也沒開放網站去改設定）。
- **名字中間有空白**：維持拆成兩個人。
- **列對狗**：一律用編號對應，沒有編號才用犬名，不用列號。

## 補 0008：Cron 寫入算進預算

Worker 在通知或 Cron 比對後寫 D1，只寫有差異的列，算進 0008 的每天寫入預算。試算表沒變時寫 0 列。待寫回重試成功時只改那一列的狀態。

## 實作時要守的 CPU 條件

- 只讀需要的欄（gviz `tq=select` 或 `range`），不要整張主清單 25 欄以上都讀進來。
- 表頭位置記住，不要每次都讀兩次。
- 上線前在預覽版用 Cloudflare 儀表板看 `/sheet-changed` 與 Cron 的實際 CPU time，超過 10 ms 就先放慢或再縮欄。

## 沒選的做法

- **維持試算表是正本**：四處各自為準正是這次問題的來源。
- **Drive push 通知**：要自己的網域、每天續約，不划算。

## 後果

- 0007 的「試算表是正本」「先寫試算表」、0012 的「通知只記有改、10 分鐘一次」被取代。
- GitHub Action 同步只剩非今日資料（狗清單、離所等），次數會再少。
- 新增「待寫回」狀態要寫進 `db/compact-schema.sql`。
