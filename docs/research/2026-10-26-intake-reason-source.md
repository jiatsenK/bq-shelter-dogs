# 出入所表的「原因」：入所原因有沒有現成來源可以自動帶

- 日期：2026-10-26（台灣時間）。Agent：Claude Code 研究代理。
- 問題（K）：出入所表（編號、入所日、出所日、原因）的「原因」是**入所原因**（K 2026-10-26 確認）。為什麼入所原因要一律手填？有沒有現成來源可以自動帶？
- 範圍：只讀 repo（`claude/639-stays-carry-number`，基準 `6148648`）和 GitHub #285、#333、#390、PR #392（唯讀）。沒有改程式、沒有查正式 D1、沒有寫 GitHub。正式資料筆數引用既有盤點文件（2026-10-17、2026-10-24），不是今天重查。
- 標記：每個主張附來源；從程式推得、沒實測的寫【推論】。

## 1. 給 K 的白話結論

- **目前實作跟 K 的說法衝突，而且 ADR 0021 本身也寫錯方向。** `stayTable` 在編號有離所紀錄時，把離所原因（認養／死亡…）放進原因欄（`worker/src/stays.js:38-39`）；ADR 0021 第 9 行也寫「出所日和原因有離所紀錄就自動帶」，第 10 行拿墨西哥「整修移所」當沒編號那列的原因。K 其實在 2026-10-19 就回答過「紀錄的原因＝入所原因」（#390 留言「核對表（K 勾選）」第 1 點）。要改 ADR 0021 和 `stayTable`。
- **能自動帶的現成來源幾乎沒有：**
  - 試算表主清單、「已出所」分頁都**沒有入所原因欄**（第 3 節）。
  - D1 `v3_intake_events`（入所事件）形狀對，但正式庫只有 **1 列**（2026-10-24 盤點），而且是志工手填、文字自由、同一編號可以好幾筆、還混著「被認養」「領養退回」這種非入所事件（第 2 節）。
  - 真正有資料的是**入所介紹文字**（`v3_intros`，127 隻，106 隻開頭是「YYYY年M月D日＋原因」）。但 ADR 0011 不准從介紹自動抓日期，只能當建議值給人確認（第 5 節）。
- **建議：入所原因仍以手填為正本，但編輯時帶「建議值」讓人按一下確認。** 有編號那列，從同編號、同日期（＝編號日期）的入所事件，或介紹裡同日期的那句帶建議；沒編號那列只帶介紹建議。不在讀取時自動填進表、不寫回。
- **離所原因不要放原因欄。** 有離所紀錄的編號，把離所原因跟出所日放一起（例如出所欄寫「2026/05/14 認養」），原因欄留給入所原因、可手填。
- **舊資料的「整修移所」「領養後退養」其實是下一次入所的原因。** 墨西哥 2017-09-05 整修移所＝編號 2017090508 那次的入所原因；JOJO「領養後退養」＝2024022801 那次的入所原因（#333 驗收步驟、#390 核對表一的寫法都支持）。舊的 6～7 筆要重新放對位置，需要 K 逐筆勾。
- **出入所表和入所介紹的逐次事件會重複。** 建議出入所表當「每次入所的原因」正本；入所介紹留給中間發生的事（被認養、退回）和描述。`v3_intake_events` 只有 1 列，可以收掉或改成只放「非入所」事件（K 決定，見第 7 節）。

## 2. D1 `v3_intake_events`（入所事件，#285）

### 2.1 欄位

`db/compact-schema.sql:170-179`：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `dog_id` | TEXT NOT NULL，外鍵 `v3_dogs` | 永久狗 ID |
| `position` | INTEGER NOT NULL | 同一隻狗的列序；主鍵 `(dog_id, position)` |
| `number` | TEXT NOT NULL DEFAULT `''` | 對應編號，**可空**（`''`＝尚未確認） |
| `event_date` | TEXT NOT NULL DEFAULT `''` | 事件日期，可空 |
| `event` | TEXT NOT NULL DEFAULT `''` | 事件文字，可空 |

表上註解：「一次入所／退回／轉所一列，保留未確認的日期與事件空白。原介紹仍留在 v3_intros，不自動解析或以編號日期覆寫」（`db/compact-schema.sql:170-171`）。

### 2.2 驗證規則（`worker/src/intake.js:2-20` 的 `cleanIntakeEvents`）

- 一隻狗最多 30 列；事件文字合計最多 1000 字。
- `number` 可空；有填要 1～32 個英數字。`date` 可空；有填要合法 `YYYY-MM-DD`。
- 開頭註解：「日期是人工確認的事件日期，不從編號推定；編號可以未確認」（`worker/src/intake.js:1`）。
- 寫入時再檢查 `number` 要屬於這隻狗（`worker/src/dog-edit.js:159`）。

### 2.5 跟編號的關係

- `number` **可空**；**一個編號可以好幾筆**（`docs/design/history/285-intake-events.md:41`「同一編號可以對應多次事件」；`tests/detail-editing.cjs:99-100`）。
- 事件日期和編號日期**刻意分開**，可以不同（`worker/test/intake-events.test.mjs:63`：編號 2024022801 配 2023-02-28）。
- 事件不只入所：「被認養」「領養退回」也放這裡（上表）。所以「這個編號的事件」≠「這個編號的入所原因」。

- 2026-10-24：**1 列**，那隻狗沒有 `v3_stays`（`docs/research/2026-10-24-521-d1-tables-audit.md:118`）。同一行已標「跟 `v3_stays` 是兩套重疊的出入所記法……是否收斂成一套是 K 的領域決定」，第 275 行列為待決。

## 3. 試算表有沒有入所原因欄

- **主清單**：GAS 只認 `籠位、編號、犬名、遛狗日期、誰遛的、備註`（`apps-script/sheet-write.gs:13` 的 `HEADERS`），送 Worker 的也只有這些（`apps-script/sheet-write.gs:518-523`）。沒有入所原因。
- **已出所**：GAS 把整列文字（`texts`）和看起來是出所日的欄（表頭含 出所／離所／認養／領養／死亡，`apps-script/sheet-write.gs:417`、`:538`）送出（`:544-546`）。Worker 只用它判讀**離所原因**（`worker/src/dog-list.js:140-143` → `worker/src/departure-rules.js:92-114`，關鍵字表 `:44-48` 只有認養／死亡／其他）。沒有入所原因欄，也沒有程式從這裡判讀入所原因。
- `v3_sheet_main.intro` 欄存在但正式庫全空（`docs/research/2026-10-24-521-d1-tables-audit.md:80`）。
- 2026-10-17 盤點與 #390 盤點留言都寫「試算表沒有入所原因欄」（`docs/research/2026-10-17-intake-records-audit.md:7`、`:23`）。ADR 0006 也不允許網站寫其他欄（同檔 `:23`）。

【推論】「已出所」分頁的整列文字裡偶爾會有入所相關字（例如退回），但目前只當離所判讀的「待確認」訊號（`worker/src/departure-rules.js:53`、`:73`），不是可靠的入所原因來源。

## 4. `v3_stays` 舊資料的 reason 被當成什麼

- **盤點結論（#390／PR #392，2026-10-17）**：6 筆 `v3_stays` 全是「整修移所」（墨西哥、蘇打、黑森林、錢錢）或「領養後退養」（JOJO、果果），寫的是「這段在所**怎麼結束**、為什麼換號」，不是怎麼入所；墨西哥的入所原因「迷路」只在介紹裡（`docs/research/2026-10-17-intake-records-audit.md:69-84`）。
- **K 的回答（#390 留言「核對表（K 勾選）」，2026-10-19）**：「紀錄的原因＝**入所原因**」。表一提議 6 筆改成入所原因（例：墨西哥「整修移所」→「迷路入所」，「整修移所」改記為 2017/09/05 那次的事件）。表上勾選框沒勾；#390 於 2026-10-21 關閉，留言「正式資料逐筆核對若需要，另開新票」。**這 6 筆從沒改過。**
- **畫面處理（PR #392）**：`intakePresentation` 把有出所日、原因是「整修移所」「領養後退養」的當成**結束原因**，顯示在出所日；其他原因當入所原因，加「入所」字尾（`public/js/detail-intro.js:39-47`；`docs/design/history/390-intake-presentation.md:9`「其他原因照已確認的入所原因呈現」）。
- **表單提示字**：出入所表原因欄 placeholder「例：迷路、退養、整修移所」（`public/js/detail-stays.js:51`，#639 前同字，`70ff450` 的 `detail-stays.js:24`）。「迷路」是入所原因，「整修移所」是盤點認定的結束原因，「退養」兩邊都可能。提示字本身就混用。
- **ADR 0011 原意**：原因例子「流浪、迷路、退養、轉所、整修暫住」（`docs/adr/0011-intake-date-manual-backfill.md:11`），偏入所原因。
- **#333 驗收步驟**（K 的原始想像）：墨西哥「新增一筆：入所 2015/8/18、原因迷路，再新增一筆整修移所的出所日和再入所日」。第二筆的「整修移所」是**再入所那次的原因**。
- 2026-10-24 正式庫 `v3_stays` 7 列（`docs/research/2026-10-24-521-d1-tables-audit.md:119`），多出的一筆沒有盤點內容。

**結論**：舊資料的「整修移所」「領養後退養」照入所原因的定義，應該是**下一次入所（新編號那列）的原因**；前一段（多半沒編號那列）的入所原因在介紹裡（迷路、被棄養…）。例：

| 狗 | 現在存的 | 改成入所原因後【推論，要 K 勾】 |
|---|---|---|
| 墨西哥 | 2015-08-18～2017-09-05 整修移所 | 沒編號 2015-08-18～2017-09-05「迷路」；2017090508「整修移所」 |
| JOJO | 2019-04-24～2024-02-28 領養後退養 | 沒編號（或 2019042401）2019-04-24～2024-02-28「被棄養」；2024022801「領養後退養」 |

## 5. ADR 與 GLOSSARY 的規定

| 來源 | 規定 | 對本題的影響 |
|---|---|---|
| ADR 0005（`docs/adr/0005-intake-date-from-oldest-number.md:9`） | 入所日看編號，不從入所介紹的文字猜日期 | 介紹文字不能當日期來源 |
| ADR 0011（`docs/adr/0011-intake-date-manual-backfill.md:11`、`:14`、`:17`） | 出入所紀錄＝入所日、出所日、原因；任何人都能補改刪、記編輯紀錄；**不從入所介紹的文字自動抓日期**（日期不一定是入所日、年份會打錯，百吉、土撥鼠差 365 天） | 只禁抓**日期**，沒禁原因；但要用介紹的原因對到某一列，得先讀介紹裡的日期來對，這就碰到這條，只能當建議值（同 `docs/research/2026-10-17-intake-records-audit.md:12`、`:96`） |

| GLOSSARY「出入所紀錄」（`GLOSSARY.md:69-71`） | 每次在所一筆：編號、入所日、出所日、原因；一個編號一筆 | 「原因」沒說是入所還是離所，要補 |

## 6. 能不能自動帶：規則與邊界

### 6.1 有編號那列

候選來源，依可信度：

1. **`v3_intake_events` 同編號、同日期的那筆**：`e.number === row.number` 且 `e.date === numberDay(row.number)`（或 `e.date` 空），而且 `e.event` 不是空字串。
   - 一個編號多筆時：只有**剛好一筆**符合才帶；多筆或日期對不上（例：`worker/test/intake-events.test.mjs:63` 編號 2024022801 配 2023-02-28）就不帶，留給人選。不能取「第一筆」，因為同編號下也可能是「領養退回」（`tests/detail-editing.cjs:100`）。
   - 文字照存（例「被棄養入所」）；要不要去掉「入所」字尾是呈現問題，`intakePresentation` 的反向規則見 `public/js/detail-intro.js:43`。
   - 實際效果：正式庫只有 1 列（2.6 節），幾乎帶不到東西。
2. **入所介紹裡日期＝編號日期的那句**（`YYYY年M月D日……` 規則，跟 `public/js/detail-intro.js:25-33` 同一套）。106 隻有這種開頭，但 24 隻介紹日期比編號早（`docs/research/2026-10-17-intake-records-audit.md:59`），也就是第一句多半是**沒編號那段**的原因，不是目前編號的。日期剛好相等的才帶。
   - 受 ADR 0011「不自動抓日期」限制：只能在編輯表單當建議值，人按了才存。
3. **都沒有**：留空，畫面寫「—」（現狀 `public/js/detail-stays.js:30`）。

**不建議在讀取時（`stayTable`）自動填進原因欄**：會讓「人確認過的」和「程式猜的」混在一起，也違反 ADR 0011 的精神；建議放在編輯表單（志工 `detail-stays.js`、管理 `admin/public/js/dog-editor.js:332`）的「建議：迷路入所［帶入］」。

### 6.2 沒編號那列

- 入所日是手填的，入所事件也多半沒編號。可以用「事件日期＝這列入所日、事件沒編號」或「介紹裡日期＝這列入所日的那句」當建議值，規則同上。
- 沒有其他來源；正本是手填。

### 6.3 離所原因放哪

- 離所原因來源已經很清楚：`v3_dog_departures.reason`（試算表「已出所」判讀，`worker/src/stays.js:111`、`:122`）。
- 建議出入所表有離所紀錄那列：**出所欄**寫日期＋離所原因（例「2026/05/14 認養」或兩行），**原因欄**仍是入所原因、可手填。
  - 這樣有離所紀錄的編號也能補入所原因；目前 `cleanStayTable` 對這種列直接丟掉送來的原因（`worker/src/stays.js:69-70`），`storedStays` 也不存（`:47`），要一起改。
- 沒有離所紀錄、手填出所日的列（舊編號、沒編號）：只有出所日，沒有離所原因欄位。結束原因（整修移所、領養後退養）照第 4 節，改記成下一列的入所原因。

### 6.4 出入所表與入所介紹會不會重複

- 會。`intakePresentation` 已把出入所表的手填列轉成「日期＋原因入所」再跟入所事件去重（`public/js/detail-intro.js:39-47`），但它刻意不讀有編號、只有編號日期的列（`:38-39` 註解「#639 刻意不改閱讀畫面」）。原因欄改成入所原因、而且有編號那列也可填之後，同一次入所會出現在：出入所表的列、入所介紹的事件（若有人填）、介紹文字開頭那句。
- 建議分工【推論，要 K 決定】：
  - **出入所表**：每次入所一列，入所原因的正本（日期、編號、原因、出所）。
  - **入所介紹**：描述與中間發生的事（被認養、退回日期、受傷）。閱讀畫面列事件時，跟出入所表同日同原因的去重（現有 `covers` 邏輯可沿用，`public/js/detail-intro.js:49-61`）。
  - **`v3_intake_events`**：只有 1 列。選項：(a) 收掉，那 1 列人工搬到出入所表或介紹；(b) 保留但只放「非入所」事件。兩套並存是 2026-10-24 盤點已標的待決（`docs/research/2026-10-24-521-d1-tables-audit.md:118`、`:275`）；2026-10-17 盤點也建議「二選一，不要兩張並存」（`docs/research/2026-10-17-intake-records-audit.md:116`）。

## 7. 要 K 決定的事

1. **確認並修 ADR 0021 第 9、10 行**：原因欄＝入所原因；離所紀錄只帶出所日（＋離所原因顯示在出所旁），不帶進原因欄。GLOSSARY「出入所紀錄」的「原因」改成「入所原因」。
2. **離所原因怎麼顯示**：出所欄寫「日期＋認養」？還是另開一欄「離所原因」？（志工手機寬度只放得下四欄，建議前者。）
3. **有離所紀錄的編號，入所原因可不可以手填**？（現在送來的原因會被丟掉。建議可以。）
4. **要不要做「建議值」**：從入所事件／介紹裡同日期的那句帶建議，人按了才存（ADR 0011 只准這樣）。還是維持純手填？
5. **舊資料 6～7 筆重放**：「整修移所」「領養後退養」改成下一列（新編號）的入所原因，前一段改填介紹裡的入所原因（迷路、被棄養…）。#390 核對表一沒勾過，要重新逐筆勾；2026-10-24 多出的第 7 筆要先看是哪隻。
6. **`v3_intake_events` 留不留**：收掉（那 1 列人工搬）、或只放非入所事件。
7. **原因要不要固定選單**（迷路、棄養、通報、拾獲、轉所、政府捕捉、退回、整修移所、其他），還是自由文字（2026-10-17 盤點第 3 題，沒答過）。選單才能做分析頁依原因分組。
