# D1 讀取量原型實測（歷史資料包＋今天紀錄＋記憶體快取）

2026-10-16，分支 `prototype/d1-read-reduction`（丟棄式，不合併）。所有數字都是原型 D1 `bq-shelter-dogs-proto` 回傳的 `meta.rows_read`，用 `wrangler dev --remote` 跑在 Cloudflare 上（不是本機模擬），沒有碰正式 D1。

## 結論

- **現在的 `/api/walks` 每次讀 4,884 列 = 溜狗紀錄 2,442 列 × 2。** `ORDER BY` 要排序，D1 把讀到的列再算一次。`/api/dogs` 每次 687 列。
- **新做法一天 1,014 列（同一台機器一直有快取）～ 26,137 列（每次都是新機器、完全沒快取的最壞情況）。現在的做法同一天 2,522,716 列。** 真實情況在兩者之間，最差也只有現在的 1%。
- 新做法的 4 支 API 輸出和現在逐字元比對完全相同（一天開始前、登記 30 次溜狗之後都比過）。
- `COUNT(*)` 照掃過的列計費（整張表 2,442 列就算 2,442）；`LIMIT n` 只算 n 列，但前提是不用排序或排序剛好走索引，否則整張表照算（見下表）。

## 模擬一天

早上 7 點到晚上 9 點，1,400 次 API 請求（假設：首頁一次讀 dogs＋walks＋rest，所以 dogs／walks／rest 各 450、departures 50），中間登記 30 次溜狗；前一晚重算一次資料包。原始輸出：`2026-10-16-d1-read-prototype-sim.json.txt`。

| | dogs | walks | rest | departures | 合計 |
|---|---:|---:|---:|---:|---:|
| 現在 | 309,150 | 2,212,566 | 450 | 550 | **2,522,716** |
| 新做法，有快取（1 台機器） | 315 | 259 | 387 | 53 | **1,014** |
| 新做法，每次都沒快取（最壞） | 8,300 | 8,287 | 8,577 | 973 | **26,137** |

另加：重算資料包 5,585／次、登記溜狗 60（30 次）。

**跟正式環境對不上的地方**：這個假設下「現在」一天要 252 萬列，但正式量到的是 66–74 萬列。換算回來，正式環境一天大概只有 130–150 次 `/api/walks`，「1,400 次請求」應該包含照片、網頁檔案等不碰 D1 的請求。要拿確切比例得看 Cloudflare 的請求分析；但不管比例多少，新做法每個請求最多讀 1＋1＋今天的列數，量級不變。

## 設計要修正的地方

1. **今天紀錄不要在 SQL 排序**：讀出來在 Worker 裡排，135 列就是 135，不是 270。原型這樣做，輸出仍完全相同。
2. **一定要加 `walk_date` 索引**，不然照日期讀還是整張表 2,442 列。
3. **資料包只在歷史資料真的變了才重算**（一次 5,585 列）。一天重算 100 次就吃掉 56 萬列，等於沒改。要跟 ADR 0008（有改才同步）配合。
4. **過了午夜不必立刻重算**：原型讀「資料包切點之後的所有列」，資料包晚一點重算也不會漏紀錄，只是多讀幾天的列（每天約 30–100 列）。
5. **別用 `COUNT(*)` 當版本號或狀態**：目前 `/api/` 狀態頁的 `compactStatus` 就是三個整表 `COUNT(*)`，每次 2,686 列。
6. **資料包大小**：現在 187 KB（溜狗紀錄佔 165 KB），D1 一列上限 2 MB。照目前每月增加約 80 KB 的速度大約 2 年會到上限，屆時要拆成幾列（例如按月）。
7. 記憶體快取在 Cloudflare 上能活多久、同時有幾台機器，原型量不到；所以上表給「有快取」和「完全沒快取」兩端。

## 怎麼重跑

```
git switch prototype/d1-read-reduction
npx wrangler dev --remote --config wrangler.d1read.jsonc --port 8799
node scripts/prototype/d1-read-sim.mjs
```

原型 D1 的溜狗紀錄是 `proto-seed.sql`（1,221 列）再複製一份往前移 31 天，湊到和正式相近的 2,442 列；另外加了 `proto_walks_date` 索引和 `proto_pack`、`proto_versions` 兩張表，模擬時寫進今天（2026-10-17）30 列。

## 第二輪：快取失效與同步（K 要求：不確認這些可能高估節省效果）

程式：`worker/prototype/d1-read/inval.js`。所有數字一樣是原型 D1 回傳的 `rows_read`／`rows_written`。

### 失效機制

- **版本號由 D1 觸發器自動加**：資料包用到的 10 張表（主清單、介紹、休養、舊編號、分組、離所等）每改一列，`small` 版本號 +1；不靠每個寫入功能自己記得改，所以不會漏。
- **資料包拆兩份**：`small`（狗清單、離所、休養）和 `walks`（今天以前的溜狗紀錄）。
- **溜狗紀錄的觸發器看日期**：改到「資料包切點以前」的列才動歷史版本號，今天的列只動 `live` 版本號。第一版不分日期，結果今天新增一筆就把 2,477 列的歷史資料包整份重算，這是第一輪漏掉的問題。
- **誰重算**：發現版本號變了的那台機器先讀 D1 裡的資料包（1 列），已經是最新就直接用，不是才自己重算再寫回去。

### 每種改動實際的代價

| 改動 | 寫入時多寫幾列（觸發器） | 下次讀 API 時讀幾列 | 輸出和現在相同 |
|---|---:|---:|:-:|
| 只改主清單第 0 列的同步時間（**每次同步都會**） | +1 | 702–707（重算 small） | ✅ |
| 改介紹 | +1 | 703 | ✅ |
| 改休養 | +1 | 707 | ✅ |
| 改過去的溜狗紀錄（例如合併志工改代號） | +1 | 2,478（重算 walks） | ✅ |
| 新增今天的溜狗紀錄 | +1 | 33–34（只重讀今天） | ✅ |
| 一次差異同步改 30 列（溜狗 20＋主清單 10） | +30 | 3,186（兩份都重算） | ✅ |
| 隔天、資料包還沒重算（切點停在昨天） | — | 34（讀昨天＋今天） | ✅ |
| 資料包已是最新、沒快取的新機器 | — | 34 | ✅ |

觸發器的成本是「每改一列多寫 1 列」。差異同步單次上限 500 列，最多多寫 500 列，佔每天 2 萬列寫入預算的 2.5%。

### 第一輪沒算進去、但真的會讀的東西

1. **每次同步都會讓狗清單資料包失效**：差異同步每次都會寫主清單第 0 列的 `synced_at`（`scripts/sync-diff.mjs`），所以就算試算表沒改，每次同步後也要重算 small（約 705 列）。ADR 0008 一天最多 30 次＋早上 1 次，最多約 2.2 萬列。
2. **同步程式自己就要讀 3,068 列**：`scripts/sync-compact-d1.mjs` 每次先讀 12 張整表來比對，新做法完全不影響這部分。一天 31 次就是 9.5 萬列；PR 預演（#310）也會讀一次。
3. **`/api/today`（ADR 0007，main 已經上線）每次讀今天的全部列**：實測今天 30 列讀 30、100 列讀 100。快取只有 15 秒、每台機器各自一份，網頁開著每分鐘抓一次。只要一直有手機開著，每台機器每分鐘最多讀 4 次，7–22 點平均 50 列 → **每台機器一天約 18 萬列**。這比 `/api/walks` 改完後省下的量還值得先處理，而且同樣能用「版本號＋只在變了才重讀」解決（每台每天約 900＋30×50 ≈ 2,400 列）。
4. **快取延遲**：改介紹、休養後，其他手機最慢 1 分鐘看到（現在是馬上）。改的人自己那台機器可以寫完就清掉快取，但別台機器上的手機要等 1 分鐘。這要 K 決定能不能接受。

### 修正後的一天估算（每種成本都是上面實測的單價，只有次數是假設）

| 情境 | 同步次數 S | 機器數 I | 現在（含 `/api/today`） | 新做法 |
|---|---:|---:|---:|---:|
| 安靜 | 1 | 1 | 約 271 萬 | 約 9,700 |
| 普通 | 10 | 2 | 約 291 萬 | 約 48,000 |
| 很忙 | 31 | 5 | 約 352 萬 | 約 13.7 萬 |

算法（新做法）：API 讀取 1,014×I ＋ small 重算 705×S ＋ walks 重算 2,478（早上 1 次）＋ 同步自己讀 3,068×S ＋ `/api/today` 改成版本號 2,400×I。
「現在」：API 2,522,716（第一輪模擬）＋ 3,068×S ＋ `/api/today` 180,000×I。

**結論修正**：第一輪「1,014 列」低估了新做法。算進同步和失效後，新做法一天約 1 萬～14 萬列，主要花在**同步程式自己讀整表**（S 次 × 3,068），不是 API。但不論哪種情境，都只有現在的 0.4%～4%，結論不變：值得做。

### 設計要再修正的地方（加在第一輪的清單後面）

7. 版本號用觸發器自動加，溜狗紀錄的觸發器要依日期分成歷史和今天。
8. 同步不要每次都改 `synced_at`；或把同步時間移出資料包（另外放 1 列），不然每次同步都要重算狗清單資料包。
9. `/api/today` 也改成版本號＋只在變了才重讀，這是目前 main 上最大的單一讀取來源（只要有手機一直開著）。
10. 要再省，下一步是同步程式：用版本號先判斷「試算表跟 D1 有沒有不同」，不要每次都讀 12 張整表。

### 沒能確認的部分

- 正式環境實際是哪個查詢讀最多：我試著用 Cloudflare 分析 API 查，但會用到本機的 Cloudflare 登入憑證，被權限擋下。K 可以自己看：Cloudflare 主控台 → Storage & Databases → D1 → `bq-shelter-dogs` → Metrics → Queries，依 Rows read 排序，就能看到前幾名的查詢和次數，用來核對上面的「現在」。
