# #460 CPU 測試條件 vs. 實際溜狗量

- 日期：2026-10-22（台灣時間）。Agent：Claude Code 背景研究代理。
- 問題（K）：「實際狀況有可能寫這麼多嗎？條件是同時多少人登記、多少隻狗？」
- 比較基準：#460 CPU 驗收條件「200 隻狗同時待寫回，每輪 Cron 派最多 10 隻、20 輪派完，每輪再保險掃描比對 200 隻」，P99 110.86 ms（`docs/design/history/460-d1-walk-unified.md:64-77`）。
- 範圍：只 GET 公開 API、讀 repo（分支 `claude/460-d1-unified`）。沒有寫入、部署或改程式，沒有操作瀏覽器。
- API 查詢時間：2026-10-22 16:17（台灣時間），需帶 `Origin: https://bq-shelter-dogs.jiatsen-k.workers.dev`，否則回「不接受這個網站的要求」。

## 結論

| 情境 | 每輪待派送 | 每輪保險掃描比對 | 跟測試比 |
|---|---|---|---|
| **測試條件** | 10 隻（連續 20 輪） | 200 隻 | — |
| 實際一般日（平均 45 狗次／天） | 幾乎都是 0：登記當下已派送 | 已接管狗數，最多 116 | 派送高估約 10 倍以上；掃描約 0.6 倍 |
| 實際尖峰日（84 狗次、13 位志工） | 仍幾乎是 0；只有當下派送失敗的狗才進 Cron | 最多 116 | 同上 |
| Apps Script 停擺 30–60 分鐘（推估） | 恢復後累積約 20–40 隻，每輪 10 隻、2–4 輪清完 | 最多 116（停擺時掃描本身也失敗） | 派送接近測試，但只發生在故障後幾輪 |

- **測試高估的部分：派送。** 正常情況登記後立刻派送，Cron 只撿失敗或中斷的；「200 隻同時待寫回」只有試算表長時間故障才可能，而且以現在的量，一整天也才 84 隻。
- **實際每分鐘都會發生的部分：保險掃描。** 只要有任何已接管的狗，每輪都會呼叫 Apps Script 讀回主清單並比對全部已接管狗，跟有沒有人登記無關。實際上限是在所狗數 116，不是 200，但這部分不會因為「平常沒人溜」而消失。
- 所以就算派送量降到 0，單輪 CPU 還是取決於「掃描 116 隻」。下一步量 CPU 時，建議把「只有掃描、0 隻派送」單獨量一次，才知道門檻主要被哪邊吃掉。

## 3. 由程式推導

- 登記：D1 模式一次請求只接受並派送一隻（`worker/src/index.js:1011-1014`，`ctx.waitUntil(dispatchWalk(env.DB, dogs[0], env))`）；整群登記在前端拆成逐狗請求（`docs/design/history/460-d1-walk-unified.md`、`docs/agent-log/2026-10-22-460-d1-walk-unified.md:4`）。
- Cron 每輪：先保險掃描，再取「中斷＋孤兒＋到期」合計最多 10 隻（`worker/src/walk-retry.js:11-29`）。派送失敗退避 1、2、4、8、15 分鐘（`worker/src/walk-accept.js:201`），所以同一批失敗狗不會每輪都回來。
- 保險掃描：讀所有有 `v3_walk_state` 的狗（已接管），沒有就直接跳過；有就呼叫 Apps Script `walkScan` 後全部比對（`worker/src/walk-reconcile.js:42-50`）。數量上限＝曾被網站登記過的狗，最多等於在所狗數。
- 正式 Cron 目前是每 10 分鐘（`wrangler.jsonc:35`），測試假設的是每分鐘；開關 `WALK_RETRY_ENABLED` 仍關（`worker/src/walk-retry.js:7`）。

推估（假設，非實測）：
- **一分鐘內被登記幾隻**：尖峰日 84 隻、13 位志工。整群登記一次按下最多是一整群（約 5–10 隻），所以一分鐘內 10 隻左右有可能；但這些都是當下各自派送，不會堆到 Cron。
- **Apps Script 停擺 N 分鐘累積幾隻**：若尖峰日 84 隻集中在約 2 小時，約每分鐘 0.7 隻 → 停擺 30 分鐘約 21 隻、60 分鐘約 42 隻；若集中在 1 小時則加倍（30 分鐘約 42 隻）。要累積到 200 隻，現在一整天的量都不夠。
