### 3.2 核對表的三種做法

| 做法 | 新頁面 | 優點 | 缺點 |
|---|---|---|---|
| A. 管理網站加「搬家核對」頁 | 1 頁＋API | K 在手機上也能勾 | 用一次就丟；要寫前端、API、存勾選結果的地方、測試，比搬家本身還大 |
| B. GitHub issue 勾選表（像 #390、#651） | 0 | K 習慣這種做法 | **repo 是公開的**，issue 也公開；原文有捕獲地址、「主人說會咬人」。127 隻 × 多欄也太長，不好勾 |
| **C. 一次性腳本產 CSV，K 用試算表軟體勾【建議】** | 0 | 不寫網站程式；每隻一列：狗、編號、原文、建議放哪一列、建議入所原因、勾選／改寫欄；K 改完存回 CSV，腳本照它產 migration SQL | 要在電腦上勾；檔案要放在不進 git 的地方（例如 `.scratch/`，現在 `.gitignore` 只排除 `.scratch/checks/`，要確認或改放 repo 外） |

做法 C 的細節：

- 產表腳本只跑 SELECT（跟上一份研究第 3 節同一組查詢），建議值規則沿用上一份研究第 7 節第 2 點（日期＝某個編號日期 → 那列；對不上 → 沒編號的新列；沒日期 → 目前編號那列；多件事的 7 隻只列原文不給建議）。
- migration SQL 會 commit 進公開 repo，所以**只放新的入所原因（地址已拿掉）**；要記進修改紀錄的「改前」原文，用 `INSERT … SELECT intro FROM v3_intros` 在資料庫裡抄，不要把原文寫死在 SQL 檔裡。
- 腳本本身可以 commit（不含資料），也可以只放 `.scratch/` 用完就丟。

## 4. 建議順序（最少重工）

### 4.1 現在就停的

- **不要做 #650 的建議值功能**、**不要照 #651 在管理網站逐隻改那 7 筆**：兩個都會被核對表＋migration 取代，現在做就是重工。

- **不要再改 `intakePresentation`、`stayLines` 接事件、`bqQuote` 跳句規則**：搬完會刪。
- **PR #664 已經合併，不用做任何事。**

### 4.2 順序

1. **K 先答兩題**（核對表要用）：入所原因要不要固定選單（#650 剩下那題）；那 9 隻「從三峽／樹林／板橋被拾獲」的地名留不留（上一份研究 K 回覆第 3 點）。離所狗 8 份 `last_intro` 搬不搬也一起答。
2. **ADR**：新增「介紹只寫狗自己，入所經過在出入所紀錄」，修訂 ADR 0021 第 16 行（`docs/adr/0021-stays-carry-number.md:16`「介紹裡的逐次事件也排進來」要拿掉）、#285 的「原介紹保留」、GLOSSARY「介紹」。關 #639、#651，#650 縮成選單一題。
3. **產核對表**（腳本，唯讀，CSV 放 repo 外或 `.scratch/`）→ K 勾。
4. **PR 1（資料 migration）**：照勾的結果寫 `v3_stays`、清 `v3_intros`、處理 `last_intro`、哈囉那 1 列入所事件搬進出入所紀錄，每隻記一筆修改紀錄。套用時 workflow 自動先備份（`docs/agents/data-changes.md`「正式庫套用」）。**這時程式先不動**：閱讀時抽句找不到日期句就什麼都不做（`public/js/detail-intro.js:26-28`），所以搬完舊程式照樣能顯示【推論】。
5. **PR 2（拿掉舊程式，同一張）**：刪 `intakePresentation`、`stayLines` 的 events／`ENDING`、介紹表單事件區、`PUT /intro` 的 `events`、`bqQuote` 跳句、`v3_intake_events` 的讀寫和合併搬移、舊 `saveIntro`；介紹表單標籤改「介紹」。
6. **PR 3（DROP `v3_intake_events`）**：先加後刪的第二張。
7. 之後：#645、#656 照常排；分享另開規格票（上一份研究第 9 節）。

順序的理由：先搬資料再刪程式，中間任何時候畫面都是對的；反過來先刪程式，搬家前 106 隻的經過會從詳細資訊消失。
