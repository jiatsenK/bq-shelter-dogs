# 遛狗狀況：手機圖表研究

2026-10-17；CODEX。研究提案，未授權實作。最新版決策：資訊的「遛狗狀況」不放久未溜，改以圖表呈現；活動每場標題下直接並列出席狗，不再點進場次。底部四格與分類首頁進子頁維持。本報告只處理圖表，舊訪談的久未溜數字／跳轉不列為必做。

## 現在能算什麼

`public/js/analysis.js` 的 `parseWalks` 只取編號、狗名、日期；`monthWalks` 以狗與日期去重。`worker/src/compact.js` 的 `readWalks` 也先按內部狗 ID＋日期合併，回傳 `id/name/date` 與可能存在的 `walkers`；沒有散步時間、時長、距離。同狗同日只能解讀為「當天有紀錄」，不是實際散步趟數。[程式](../../public/js/analysis.js)、[讀取契約](../../worker/src/compact.js)、[schema](../../db/compact-schema.sql)。

API 的 `historyStart` 是 2026-09-25；更早的日期可能只是首次匯入的最後一次遛狗日。現有 `monthWalksSection` 用最早日期當開始日，會混淆這兩種資料，不能照搬。正式 API 唯讀查詢遭環境通訊端限制，未取得即時統計；fixture 只能驗證形狀，不能代表正式分布。也尚無每日同步完整性的證據，開始累積不等於每天完整登記。

## 業界依據與候選

官方指南主張先選要回答的問題，再選圖；分布適合長條，圖表應保留清楚標籤與可讀替代資料。[UK Analysis Function](https://analysisfunction.civilservice.gov.uk/policy-store/data-visualisation-charts/)。Datawrapper 指出，固定區間重新累計的少量時間資料，直條較容易比較；折線偏向連續變化。[Datawrapper Academy](https://www.datawrapper.de/academy/what-to-consider-when-creating-line-charts)。以下是依這些原則對本資料的推論，不是官方替本產品選圖。

| 圖表／回答的問題 | 欄位與計算 | 可行性與限制 |
|---|---|---|
| **每日已記錄遛狗隻數直條**：哪天帶了較多狗？ | 本月各日期的 distinct 狗數；跨日相加稱狗日 | 現有 walks 可算，不需新 API；不稱趟數，不含未來日 |
| **目前在所狗被記錄天數橫條分布**：照顧集中在哪些狗？ | 目前狗清單逐狗計 distinct 日期，再分「無紀錄、1天、2–3天、4天以上」 | 不需新 API；區間只是示意，應看正式分布調整；新入所狗可觀察天數較少，不是公平性排名 |
| **本月有紀錄比例條**：目前在所狗有多少被記錄過？ | 分子是目前清單與本月 walks 的交集，分母是目前清單可辨識狗數 | 條件可算，不是全月在所犬的真正涵蓋率；離所狗不在分母，不建議當主圖 |

## 下一版示意建議

**主圖選每日直條；輔圖選被記錄天數分布。** 前者看每天變化，後者看狗之間的分布，不重複回答同一問題。首頁摘要可先示意一張精簡每日直條；點進子頁再看主圖、輔圖與兩個數字「本月有紀錄 N 隻」「累計 N 狗日」，避免首頁塞完整報表。

手機主圖每月最多 31 根，日期只標少量刻度；數值由觸控或可展開表格取得，不依賴滑鼠懸停。輔圖直接在橫條旁寫隻數，維持單色與零基準。標題寫期間，圖下註明「同狗同日算一筆；登記紀錄不等於全部實際遛狗」。這符合官方的水平標籤、簡潔與替代文字／表格建議。[UK 指南](https://analysisfunction.civilservice.gov.uk/policy-store/data-visualisation-charts/)

缺資料分開呈現：historyStart 以前標「未開始累積」，請求失敗標「讀不到」，成功回傳後空日期只稱「未登記」，不宣稱沒人遛；今天標「截至目前」。分布的零組稱「本月無紀錄」，不能說「本月沒溜」。若要求真正每日在所涵蓋率或登記完整率，需要歷史在所名冊／同步狀態等新增資料，現有 API 不足。

暫不做上月完整對比、成長率、時段熱力圖、距離或時長。上月只有 9/25 起的累積區間，且月份天數不同；資料不足不應畫成退步。後續待確認的是圖放首頁或僅子頁，以及是否採上述主輔圖，尚未形成規格。
