# 2026-10-24 D1 資料表稽核（#521 子票 #549）

2026-10-24（台灣時間）。對象：`db/compact-schema.sql` 的 54 張表。只盤點和建議，**沒有改程式**；正式 D1 只送 SELECT（`npx wrangler d1 execute bq-shelter-dogs --remote`，每次 `rows_written: 0`）。程式以 main `2a05e25` 為準。

觸發器的逐個評估在平行的 #548（`docs/research/2026-10-24-521-d1-triggers-audit.md`，另一個 worktree）；本文只標出「表的決定會牽動哪些觸發器」。

## 結論（白話）

- **54 張表裡，8 張可以直接刪、4 張可以併進別的表**，第一階段做完是 42 張，schema 觸發器 75 → 60。再往下（第二階段、待 K 決定的項目）最多到 31 張左右，但省的多半只是「表的數目」，要看 K 要不要。
- **刪的 8 張都追過讀寫來源，沒有任何畫面在讀**：舊比對狀態 `v3_walk_compare`、空表 `v3_sheet_departed`、舊照片清單 `v3_photos`（照片在 R2）、跟身分對照完全重複的 `v3_volunteer_codes`、算得出來的 `v3_sheet_former_numbers`、0 列的舊常溜 `v3_favorites`、D1 開關打開後只剩舊網頁在寫的 `v3_today_walks` 與它的版本號 `v3_data_versions`。
- **併表挑的是「每次都整組換、整組讀」的清單**（某隻狗是誰遛的、常遛狗群一欄、離所的判讀旗標／舊編號／狗群），改成所屬那一列的 JSON 欄。以前（10/22 研究）不建議，是因為舊同步要逐列比差異；舊同步已在 #501／#512 退役，現在的寫法本來就是整組刪掉重寫，改 JSON 反而少寫很多列（改一群狗從約 54 列寫入降到約 2 列）。
- **K 指定的「我的最愛」「曾開啟的狗卡」不建議改成志工表的 JSON 陣列**：資料量小（最多一人 49 筆）、現在一次讀只要幾列；改 JSON 後兩支手機同時改要靠 SQL 內的 `json_insert`／`json_remove` 才不會互蓋，身分合併要改寫成 `json_each` 合併，還會失去對狗 ID 的關聯檢查。省下的讀取每天不到一千列，不值得。
- **順手發現 4 個要另外處理的問題**（不在本票修，見第 6 節）：正式庫的改名字／合併身分一定失敗；`/walkers` 每分鐘白讀 772 列；開卡讀回一次讀 3,011 列；之後離所的狗會掉失入所介紹。
- 刪表、併表都要搬或丟正式資料，**全部依賴 #521 前置項目「schema 變更套到正式 D1 的路徑」**，那條路做好前一張都不要動。

## 1. 怎麼查、證據來源

- 每張表都 grep `worker/src`、`public/js`、`scripts`、`apps-script`，再讀到實際的 SQL 與呼叫它的 API。前端不直接碰 D1，所以「網站有沒有在用」是看 API 回傳的欄位前端有沒有讀。
- 正式 D1 筆數：一句 `SELECT (SELECT COUNT(*) FROM t1) AS t1, …`（rows_read 3,001）。另外查了版本號列、`v3_sync_state` 的鍵、觸發器清單、幾張表互相比對的結果。
- 讀取成本：把 Worker 實際送的查詢在正式 D1 跑一次，看回傳的 `meta.rows_read`（D1 計費就是這個數字）。
- 寫入成本：依 Cloudflare D1 計費規則估（每寫一列算 1；動到索引的欄位，每個索引再加 1；觸發器裡的 UPDATE 另外算），沒有在正式庫實際寫。

## 3. K 指定的例子：常溜、開卡、小型個人設定要不要改 JSON

### 3.1 資料量（正式 D1）

| | 有資料的人 | 一人最多 | 平均 |
|---|---:|---:|---:|
| 常溜（`v3_volunteer_favorites`） | 8 | 44 隻 | 13.8 隻 |
| 開過的卡（`v3_volunteer_cards`） | 1 | 49 張 | 49 張 |

狗 ID 是 32 字元，一人 50 隻約 2 KB，遠低於一列 2 MB 的上限，**放得下不是問題**。

### 3.2 逐項比較

| 面向 | 現在：一人一狗一列 | 改成：`v3_volunteers` 一欄 JSON |
|---|---|---|
| 讀取 | 主鍵前綴，實測一人 2 隻 rows_read 3；50 隻約 50 列 | 1 列 |
| 寫入（按一次常溜） | 新增或刪 1 列（＋主鍵索引 1） | 改 1 列；`v3_volunteers` 的 `name` 有 UNIQUE 索引，但不改名就不算 |
| 兩支手機同時改 | 各自新增／刪除不同列，**天生不互蓋** | 只有寫成單句 `UPDATE … SET favs=json_insert(…)`／`json_remove` 才不互蓋；任何「先讀出來、改好再整份寫回」的寫法都會蓋掉另一支手機的改動 |
| 身分合併 | 一句 `INSERT … SELECT … ON CONFLICT DO UPDATE SET added_on=MIN(…)`（`identity.js:132-133`） | 要用 `json_each` 把兩人的清單展開、去重、取最早日期再組回去，SQL 明顯更難懂 |
| 關聯完整性 | `dog_id` 有外鍵指向 `v3_dogs` | JSON 裡的狗 ID 資料庫不檢查 |
| 開卡日、加入日 | 各一欄 | 開卡要存 `{狗ID: 日期}` 物件；常溜的 `added_on` 目前沒人讀，可丟 |
| 開卡讀回要換成編號 | JOIN 主清單（缺索引，見第 6 節） | `json_each` 後一樣要 JOIN |
| 觸發器 | 各表 3 個 `identity_*`（正式庫本來就沒有） | 改成掛在 `v3_volunteers` 上，每次按常溜都會讓身分版本加 1（現在 schema 也是，#548 會處理） |

**結論：保留獨立表。** 省下的讀取，10/22 研究 C 用 10/18 的量估一天約 3,000 列，約免費額度（每天 500 萬列）的 0.06%；換來的是並行要靠特定 SQL 寫法才安全、合併身分變難、失去外鍵。不符合「不能為了少幾張表讓程式變複雜」。

可選的折衷（不建議現在做）：常溜與開卡主鍵都是 `(volunteer_id, dog_id)`，可併成一張 `v3_volunteer_dogs(volunteer_id, dog_id, favorite_on, opened_on)`，少 1 張表、3 個觸發器，合併身分只要一句。代價是取消常溜要改成「把 `favorite_on` 設成 NULL，兩欄都空才刪列」。省得很少，列為選項。

### 3.3 其他小型個人設定

志工的名字、代號存在手機（`appState.phoneStore`，`public/js/app.js:236-241`、`:893-897`），D1 只有上面兩種個人資料。`v3_volunteers.last_seen` 只給名字建議排序用，是一般欄位，沒有要改的。

## 6. 順手發現、要另外處理的問題（本票不修）

1. **正式庫的改名字、合併身分一定失敗。** `v3_identity_revision` 0 列，`renameIdentity`／`mergeState` 讀 `(…).revision` 時丟 TypeError（`identity.js:56`、`:97`），被 `identityRoute` 接住回 409「身分資料已變動，請重新檢視」（`index.js` 的 `identityRoute` catch）。前端有這個功能（`public/js/welcome.js:19-46`）。正式庫 `v3_identity_operations` 0 列，表示從沒成功過。修法是補一列預設值（屬「寫正式 D1」，要 K 執行或走 schema 套用路徑）。
2. **`/walkers` 每次重讀白讀 772 列。** walkers 三表 JOIN 只在 `walker IS NULL` 時有用，正式庫已是 0 列（`index.js:755`、`:769`）。不等併表也能先拿掉。
3. **開卡讀回一次 3,011 列、觸發器每次掃 116 列。** `v3_sheet_main` 沒有 `dog_id` 索引；10/22 研究 B 已建議，還沒做。
4. **之後離所的狗會掉失入所介紹。** 記離所時 `last_intro` 抄 `v3_sheet_main.intro`（`dog-list.js:158`、`:162`），這欄在正式庫全空；介紹其實在 `v3_intros`。現有 8 筆離所是舊同步記的，介紹還在；#501 之後新記的離所會是空的（推論，沒有在網站上看過畫面）。

## 7. 依賴：schema 套用路徑與搬資料

除了「補索引」「補 `v3_identity_revision` 那一列」可以用 `CREATE INDEX IF NOT EXISTS`／`INSERT OR IGNORE` 安全重跑，其他全部要搬或丟正式資料，**必須等 #521 前置項目（schema 變更套到正式 D1 的路徑）做好**：

| 項目 | 正式庫要做的事 | 還原 |
|---|---|---|
| 刪 8 張表 | DROP（`v3_photos` 128 列、`v3_card_opened` 若刪 48 列，建議先匯出） | 從匯出檔或 D1 Time Travel 還原 |
| `v3_sheet_main` 刪 7 欄 | `ALTER TABLE … DROP COLUMN` | 欄位值都是複本或沒人讀，可由程式重建 |
| walkers、狗群改 JSON | 新欄／新表，從舊列組 JSON，再刪舊表 | 舊表先留一版不刪，確認後再 DROP |
