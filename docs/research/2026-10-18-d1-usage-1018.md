# 2026-10-18 正式 D1 讀寫用量：誰在讀、誰在寫、晚間尖峰哪來的

2026-10-18（台灣時間）。問題：主控台最近 24 小時讀 117.65k、寫 1.86k，Top query「SELECT number, dog_id FRO…」讀 22.31k；
晚間約 19 點有讀約 1 萬、寫約 700 的尖峰。要找出每小時用量、前幾名查詢對應的程式、尖峰原因，以及對 #402 的意義。

查詢時間：10/18 19:33（台灣）。所以「10/18 一整天」實際只涵蓋 00:00～19:33，20 點以後還沒發生。
主控台的 117.65k 是「往回 24 小時」（含 10/17 晚上），跟本文的「台灣日曆日 10/18」不同區間，數字不能直接相減。

## 資料來源與查法

- Cloudflare GraphQL Analytics API `https://api.cloudflare.com/client/v4/graphql`，用 wrangler 的 OAuth token（不落檔、不印出）。
  資料集與欄位見官方文件 https://developers.cloudflare.com/d1/observability/metrics-analytics/ 。
- 每小時用量（`datetimeHour_geq: 2026-10-17T16:00:00Z` = 台灣 10/18 00:00）：

  ```graphql
  {viewer{accounts(filter:{accountTag:"a0f88d34c34ad0d34f923b9f43799622"}){
    d1AnalyticsAdaptiveGroups(limit:100,filter:{databaseId:"6cd6c304-0fed-4ddb-b9ec-799e60a4adb4",
      datetimeHour_geq:"2026-10-17T16:00:00Z",datetimeHour_lt:"2026-10-18T16:00:00Z"},orderBy:[datetimeHour_ASC]){
      dimensions{datetimeHour} sum{rowsRead rowsWritten readQueries writeQueries}}}}}
  ```

- 各查詢（同一區間，`orderBy` 換成 `sum_rowsWritten_DESC` 就是寫入排行；把時間窗縮到單一小時看尖峰）：

  ```graphql
  {viewer{accounts(filter:{accountTag:"a0f88d34c34ad0d34f923b9f43799622"}){
    d1QueriesAdaptiveGroups(limit:30,filter:{databaseId:"6cd6c304-0fed-4ddb-b9ec-799e60a4adb4",
      datetime_geq:"2026-10-17T16:00:00Z",datetime_lt:"2026-10-18T16:00:00Z"},orderBy:[sum_rowsRead_DESC]){
      count dimensions{query} sum{rowsRead rowsWritten}}}}}
  ```

- 同步執行時間：`gh run list --workflow sync-sheet.yml --limit 30`；同步摘要：`gh run view 39121568125 --log`。
- 注意：兩個資料集都是 Adaptive（取樣）資料，單一小時的加總和查詢排行會有出入（例：06 時每小時用量讀 9,341，但同小時查詢排行光 `v3_intros` 就 14,632）。下面以「量級與排名」為準，不當精確帳目。

## 3. 「SELECT number, dog_id…」是不是 narrowSeedSql 整張掃？

**不是。** 那是 Worker 的 `favoriteAliases`（[compact.js:126-135](../../worker/src/compact.js#L126)），每次讀常溜就整張讀 `v3_dog_numbers`。主控台的「一次讀 22.31k」是 24 小時的累計，不是單次；單次只有 132 列，問題在**次數多**（今天 137 次）而且每次都附帶 `v3_dogs` GROUP BY（讀更多，268 列／次，是今天讀最多的查詢）。

ADR 0014 第 56 行懷疑的 `narrowSeedSql` 掃 `v3_walks`：
- `#372`（commit `8cd3e3d`「同步讀溜狗紀錄、離所強制走日期索引，不再整張掃（#371）」）已把 `walksSql` 和離所改成 `INDEXED BY`（[sync-compact-d1.mjs:70](../../scripts/sync-compact-d1.mjs#L70)、[127](../../scripts/sync-compact-d1.mjs#L127)）。
- 但實測 `v3_intros` 那句每次仍讀 1,829 列（8 次 14,632），而介紹表本身只有百來列，代表 `dog_id IN (… UNION …)` 子查詢仍掃了不少列（推測是 UNION 四段每段各算一次、或 `v3_dog_numbers`／`v3_sheet_main` 被反覆掃）。同一個 `dogIds` 也用在 `v3_dogs`、`v3_dog_numbers`（[sync-compact-d1.mjs:136-137](../../scripts/sync-compact-d1.mjs#L136)），但那兩句今天沒進排行，原因待用 `EXPLAIN QUERY PLAN` 確認。
- 結論：ADR 0014 說的整張掃 `v3_walks` 已修；`v3_intros` 那句還有約 1.8k 列／次的殘留，量不大（一天同步幾次 ≈ 數千～1.5 萬列）。

## 4. 晚間尖峰是什麼造成的

`gh run list --workflow sync-sheet.yml` 10/18 的兩次（換成台灣時間）：

| run | 開始 | 結束 | 觸發 | 結果 |
|---|---|---|---|---|
| 39075350888 | 10/18 06:30 | 06:31 | workflow_dispatch（Worker 叫的 6:30 保險同步） | success |
| 39121568125 | 10/18 19:01 | 19:02 | workflow_dispatch（Worker 偵測到試算表被手動改，ADR 0012） | success |

19:01 那次的摘要（`gh run view 39121568125 --log`）：「已同步：寫入 231 列（今天帳號已寫 718 列）。共 118 隻狗、比對 2026-10-17 以後的 134 筆溜狗紀錄、6 筆離所、11 欄常遛狗群。」

所以 19 時的 707 寫 ≈ 同步匯入 231 列（含索引、`packs_*` 觸發器各多算的列，D1 規則見 pricing 頁「每個索引多算 1 列寫入」）＋同小時網站 `v3_volunteers` upsert 80 列等。讀的 10,810 則是同步讀 seed、加上同步讓資料包失效後 Worker 重算（排行第 9、10 名、`v3_sheet_main_walkers` 726、`readDogsPayload` 705）與晚間網站使用（`favoriteAliases` 3,216＋660）。

231 列「差異」偏多：試算表沒大改時差異同步理論上只寫有變的列（ADR 0008、sync-sheet.yml 開頭說明），這次可能是溜狗群、主清單或常遛群整欄被重寫，值得看 diff 明細確認（待查）。

## 5. 對 #402（白天 GAS 差異／半夜 D1 同步）的意義

`gh issue view 402`：K 的主要顧慮是免費額度，怕按更新觸發同步；驗收要求「分別估算或實測 … D1 讀寫（含索引／觸發器）」。今天的實測可直接當基準：

- **整天 D1 用量只有額度的約 1.5%**（讀 8.2 萬／500 萬、寫 1,490／10 萬）。以額度而言，現行架構沒有壓力，改架構不是為了 D1 額度。
- **一次試算表同步 ≈ 讀 1 萬列、寫 200～700 列**（06 時、19 時兩個樣本）。即使一天跑滿 12 次同步上限＋1 次保險，約讀 13 萬、寫 9,000，仍在額度 3%／9% 內。寫入才是比較接近天花板的那邊，且寫入量主要取決於「差異大小＋索引／觸發器加成」，不是同步次數本身。
- **網站自己的讀寫比同步大**：讀的三分之二來自 `/api/favorites` 的 `favoriteAliases`，寫的大宗是 `rememberWalkerNames` 的 upsert（403 列）和今日溜狗。把同步改成半夜一次，只省得到同步那塊（今天約 2 萬讀、約 900 寫），網站這塊不變。
- 對 #402「GAS 提供差異是否真的省」：今天的數字顯示 D1 端可省的空間有限；比較時更該看 GitHub Actions 分鐘（每次同步約 40～60 秒，見 run list）、GAS 配額與可靠性，而不是 D1。
- 限制：只有一天、而且是週日；平日人數、手動改表頻率不同時要再量。
