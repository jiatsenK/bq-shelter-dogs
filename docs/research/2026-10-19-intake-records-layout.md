# #390：讓出入所紀錄與入所介紹保持精簡

## K 已確認的呈現方向（2026-10-19，取代下方研究建議）

K 否決本文件原先建議的展開入口、原介紹切換，以及後續互動示意，因為增加操作與理解成本；已明確確認以下方向：

- 閱讀畫面只留一段「入所介紹」，日期與經過直接列在一起；其他補充文字接在下方。
- 有幾筆列幾筆，沒有內容不留空區；不另設出入所紀錄區、原介紹切換或展開入口。
- 同一件事只呈現一次。原文保留在資料裡供編輯核對，閱讀畫面只呈現整理後的一份。
- 此確認針對呈現方式，不代表已確認逐筆日期、資料轉換、永久 ID 合併對照或正式資料寫入；資料模型與入所日算法尚未因此變更。

```text
2015/08/18　迷路入所
2017/09/05　整修移所

其他補充文字
```

## 結論

**先減少重複，再決定哪些內容展開。** 保留入所介紹的資料，不表示每次開詳細資訊都要把介紹全文再列一次。建議一個區塊、一個摘要、一個「查看出入所紀錄與介紹」入口；展開後才看完整資料，不再維持兩段標題、兩套重複日期與兩個編輯入口。

主要畫面沿用既有「入所日／入所多久」資訊，不為這次合併再加一份摘要卡。歷史資料入口用純文字與展開指示，沿用白紙、細線、字重的層級。戶外帶狗需要的警示、限制與已確認的重要個性資訊保持可見，不能一律當歷史收起。這是依本案需求作的設計判斷；依據見下方來源與專案約束。

## 問題在內容結構

本機 `public/js/app.js` 的 `introSectionHtml` 同時顯示 `intakeEvents` 與 `intro` 全文；`staysSectionHtml` 另列出入所紀錄及編輯入口。沒有補登但可編輯時，後者仍會顯示一整段空狀態。這會讓同一次入所在兩處出現，並讓尚無內容的狗也增加高度。對照原始碼：`intakeListHtml`、`introSectionHtml`、`staysSectionHtml`、`renderDetail`。

`docs/DESIGN_GUIDE.md` 已要求詳細資訊是一張白紙、段落以細線區隔，避免過多方格；新增／編輯就地展開、觸控區至少 44×44px。`docs/PROJECT_GOALS.md` 的核心仍是現場判斷誰該溜、備註與同行關係。以上支持降低歷史資料的預設重量，而非縮字塞滿。

## 方案比較

| 方案 | 優點 | 成本／問題 | 判斷 |
|---|---|---|---|
| 全部事件＋完整介紹常駐 | 不必點擊即可看全部 | 重複、歷史搶走現場資訊、空狀態也佔位 | 不建議 |
| 全部改成大型時間線 | 順序清楚 | 仍長，標記、連線、卡片會增加重量；不能解決重複來源 | 不作預設 |
| 兩個獨立折疊段落 | 改動較小 | 志工仍要分辨哪份可信，也保留兩個入口 | 僅可作短期過渡 |
| 單一摘要入口、展開一份資料 | 初始高度穩定、保留查歷史能力 | 要處理來源衝突與未核對資料，並測試入口是否易找 | **優先推薦** |
| 紀錄／介紹固定分頁 | 可避免兩份全文同時出現 | 增加一層介面、名稱理解與切換成本 | 不列為必要元件 |

## 推薦的具體呈現

### 預設

沿用目前已有的入所日與入所多久；其下只留一行「查看出入所紀錄與介紹」。有人工紀錄才加筆數，且必須寫「已補登 2 筆」，不能把補登筆數說成真實入所次數。沒有介紹、沒有補登時，只留小型「補入所資料」操作，不顯示兩個「還沒有」段落。

介紹中已確認、會影響帶狗的資訊可保留短段落；不能用固定前兩行裁切代替判讀，因為重要警示可能在最後一行。這類整理須逐筆確認，不能靠這次介面研究默默搬動或改寫資料。

### 展開

一份純文字清單，日期在前、原因短句在後，長句自然換行；不用框中框或每筆一顆刪除鈕。入所原因不必同時再在介紹全文重述。出所日、未對應的介紹、編號對照等，在需要時仍能查看；原因空白就不虛構，日期未確認就明寫，不用編號推定。

**已確認對應的內容只呈現一次；未核對內容保留原文。** 資料還不能可靠對應時，不為了整齊自行合併，也不自動把介紹文字當成會影響入所日的正式紀錄。原介紹全文保留可讀入口，可用「看原介紹」在同一內容位置替換顯示，再以「回出入所紀錄」回來；不再整段附在清單下面。這個替換方式是避免同時重複展示的候選，仍有返回與焦點成本，原型需驗證；不預設新增固定分頁或巢狀折疊。

最省步驟的情況：只有介紹、沒有可靠結構化紀錄，就直接在這個展開區顯示介紹，不再顯示空的時間線或要求先切換。

### 編輯

同區只有一個「編輯入所資料」入口。按下才在原處顯示表單，平時不展示新增、刪除、來源選擇等管理控制。沿用選好名字、編輯紀錄與併發保護；只編輯一筆時，不預先把所有筆表單攤開。儲存／取消回到原位置，保留展開狀態與焦點。

這不等於先決定合併三個 API 或儲存結構；介面的一個入口與資料模型合併須分開處理。

## 邊界情況

| 情況 | 推薦行為 |
|---|---|
| 只有編號推得入所日 | 保持既有日期資訊，不生成人工事件，不列空清單。 |
| 只有介紹 | 同一入口展開原介紹；重要警示維持可見，無可靠分類前不一律收起。 |
| 一次入所 | 展開後一列足夠，不做大型時間線；來源原文不再同時重複列。 |
| 多次入所／退養／轉所 | 展開後按日期列全部已確認內容；未知日期另標示，不猜順序。 |
| 介紹與正式紀錄日期矛盾 | 保留差異與來源；只在展開／編輯處提示待確認，不自動改入所日。 |
| 介紹含咬傷、怕聲響或其他帶狗資訊 | 先逐筆核對，保持影響現場判斷的內容可見；不可只靠關鍵字或摘要模型保證安全。 |
| 已離所的狗 | 共用相同閱讀層級，保留現有可補出入所紀錄的權限，不因版面合併任意改權限。 |
| 三組雙 ID | 合併身分的既定方向保留；本研究不決定主 ID、不移正式資料。 |

## 與既有決策的關係

保留「原因指入所原因」「保留入所介紹」「三組雙 ID 合併」的已確認方向。不替使用者選 A／B／C，不把這輪研究當成已同意新的事件資料模型。

`docs/adr/0011-intake-date-manual-backfill.md` 目前仍是每次在所一筆（入所日、出所日、原因），並要求按時間列出紀錄；本提案可先調整顯示層級，不必先改成只有單一日期的事件。若之後決定移除出所日或變更入所日算法，才需要重開 ADR。`GLOSSARY.md` 的入所介紹也允許未對應資料保留，不能拿「去重」當成刪原文的授權。

## 驗證與限制

下一步應先拿本機具代表性的資料做靜態／可操作比較：單筆、多筆、只有長介紹、日期衝突、含警示、空資料、離所狗。比較開啟詳細資訊到找到入所日、看到注意事項、查看來源、編輯單筆所需步數，而非只看能省幾行。

實作時依專案規範驗證 320／390px 與電腦版、長字換行、44px 點擊區、鍵盤焦點、編輯後返回與無橫向溢出。歷史展開長度可以增加，預設頁面不應隨完整歷史成比例增長；但不能為高度指標藏起未核對的現場資訊。
