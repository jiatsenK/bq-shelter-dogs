# 板收志工溜狗表：「今天溜狗只存 D1、Cron 每分鐘讀試算表」可不可行

- 日期：2026-10-20（台灣時間）。Agent：Claude Code 背景研究代理。
- 範圍：分支 `fix/live-sheet-sync-and-resort`（PR #435）的原始碼、ADR 與官方文件。沒有操作瀏覽器、沒有改程式、沒有寫正式資料。
- 標示：**已確認**＝官方文件或程式碼直接寫的；**推估**＝照下列假設算出來的；**推測**＝邏輯上成立但要實測。
- 接續 `docs/research/2026-10-20-sync-pitfalls.md`（14 個坑）。

## 要評估的新架構

1. 「今天溜狗」只存 D1 一張表（沿用 `v3_today_walks`）；按「溜了」直接寫 D1，再由 Worker 寫回試算表。
2. 有人直接改試算表時，Worker Cron 每分鐘讀一次試算表、算差異、更新 D1。
3. 手機只顯示 D1；localStorage 只記「我剛按的先別移位」。
4. 時間由伺服器決定，不用手機時鐘比新舊。

## 結論先講

| 項目 | 判斷 |
|---|---|
| 額度（D1 讀寫、Workers 請求數） | **夠**。推估讀約 40–80 萬列／天（上限 500 萬）、寫約 1,000–2,000 列／天（上限 10 萬）、請求約 3–6 萬次／天（上限 10 萬）。 |
| 最大風險 | **Cron 每次 CPU 上限 10 ms**。ADR 0012 記錄 Worker 自己同步實測 64–152 ms；每分鐘只讀主清單兩欄會輕很多，但能不能穩定壓在 10 ms 內要實測。 |
| 第二風險 | **網站寫入與 Cron 讀到舊試算表的競爭**、**gviz 快取延遲**：不處理就會出現「剛按的溜了被 Cron 蓋回未溜」。需要「待寫回」狀態＋寬限時間。 |
| 衝突 ADR | 0007「試算表是正本」「Apps Script 先寫成功才記 D1」、0012「網站寫入不觸發同步、Worker 不自己同步」要 K 重開；0006 不衝突；0008 預算不衝突但要補「Cron 也算進預算」。 |
| 總結 | **可行，但要分階段**，先做 CPU 實測再決定每分鐘還是每 2–5 分鐘。 |

### 1-4 D1 讀取（每天，按掃描列數）

現行 `/api/today` 每次先讀 1 列版本號（`worker/src/today.js:48`），版本沒變就回記憶體快取；有變才讀今天的列（`worker/src/today.js:51`，`WHERE walk_date=?`）。

- `v3_today_walks` 主鍵是 `(walk_date, dog_key)`（`db/compact-schema.sql:236-244`），`walk_date=?` 走主鍵索引，只掃今天的列（最多約 120 列）。**不用另加索引。**
- 舊日期的列每次寫入時刪掉（`worker/src/today.js:40`），表不會長大。

| 來源 | 算式 | 讀取列數 |
|---|---|---|
| 輪詢讀版本號 | 27,000 × 1 | 27,000 |
| 版本變了重讀今天的列 | 版本一天變約 130 次（A4）× 每次被 3–10 個 isolate 各讀一次（A6）× 120 列 | 4.7 萬–15.6 萬 |
| Cron 比對：讀 D1 今天的列 | 1,440 × 120 | 17.3 萬 |
| Cron 比對：讀狗對照（`v3_sheet_main` 或 `v3_dog_numbers`，約 118–200 列），若每次都讀 | 1,440 × 200 | 0–28.8 萬（可改成記憶體快取或只在有差異時讀） |
| **合計** | | **約 25 萬–62 萬列**（上限 500 萬，約 5–12%） |

最壞情況（每次輪詢都快取沒中）：27,000 × 121 ≈ 330 萬，加 Cron 約 380 萬，仍在 500 萬內但只剩 24% 餘裕，要避免。對策：保留版本號機制（ADR 0009），Cron 沒差異時**不寫**，版本號就不會變。

### 1-5 D1 寫入（每天）

一次「溜了」寫 `v3_today_walks` 一列的實際計算：

| 寫入 | 列數 | 依據 |
|---|---|---|
| 表本身 | 1 | |
| 主鍵索引（複合主鍵、非 INTEGER PRIMARY KEY，SQLite 會建自動索引） | +1 | D1 pricing「Indexes will add an additional written row」 |
| 觸發器 `version_v3_today_walks_*` 更新 `v3_data_versions` | +1 | `db/compact-schema.sql:250-252`；觸發器裡的 UPDATE 算不算寫入官方沒單獨寫，保守算 1 列（推測） |
| 每天第一筆的 `DELETE ... walk_date<?` | 前一天約 130 列 × 2（含索引）＋觸發器每列 1 | `worker/src/today.js:40`；觸發器是 FOR EACH ROW（SQLite 預設），每刪一列版本號加 1 |

| 來源 | 算式 | 寫入列數 |
|---|---|---|
| 網站按溜了／復原 | 130 × 3 | 390 |
| 每天清前一天 | 130 × 3 | 390 |
| Cron 抓到試算表手動改 | 估每天 30 筆 × 3 | 90 |
| Cron 寫「待寫回」狀態、上次讀取指紋（`v3_sync_state` 一列，**只在有變時寫**） | 估 100 × 1 | 100 |
| **合計** | | **約 1,000 列**；若 Cron 每分鐘都寫一次狀態列則多 1,440，約 2,500 列（上限 10 萬，ADR 0008 預算 2 萬） |

**觸發器會放大寫入**：每改一列多寫 1 列版本號；DELETE 多列時每列都觸發一次。量不大，但 Cron 若用「整天刪光重寫」而不是差異寫入，會變成每分鐘 120 × 3 = 360 列 × 1,440 ≈ 52 萬列，**直接爆掉**。一定要只寫差異（ADR 0008）。

### 1-6 Google 那端

- Cron 每分鐘讀 gviz：1,440 次／天。gviz 沒有公布額度；現行 `/walkers` 已經「最多每分鐘一次」讀 Google（ADR 0007 第 26 行），新架構量級相同，**改由 Cron 集中讀反而比多個 isolate 各自讀少**。
- 主清單 gviz 現在要分兩次讀（表頭、資料，`worker/src/index.js:786-855`），每次 Cron 2 個 subrequest，加寫回 Apps Script 1 個，遠低於 50。
- 寫回走 Apps Script（`apps-script/sheet-write.gs`），一天約 130 次，遠低於配額。

## 2. 坑

嚴重度：高＝會讓顯示錯或額度爆；中＝偶爾錯、會自己修好；低＝體驗或維護問題。

| # | 坑 | 發生情境 | 影響 | 建議對策 | 嚴重度 |
|---|---|---|---|---|---|
| 1 | **Cron 讀到舊試算表，蓋掉剛按的溜了** | 10:00:05 按溜了，D1 寫好，Worker 正在叫 Apps Script；10:00:10 Cron 讀 gviz，試算表還沒寫（或 gviz 還是舊快取），算出「差異：沒溜」寫回 D1 | 所有手機看到狗閃回未溜，下一分鐘又對（或寫回失敗就一直錯） | D1 每列加 `pending`（待寫回）與 `written_at`；Cron 遇到 `pending=1` 或 `written_at` 在寬限時間（建議 3–5 分鐘，涵蓋 gviz 延遲）內的列一律跳過，不拿試算表蓋 | 高 |
| 2 | **寫回試算表失敗或很慢，誰為準** | Apps Script 逾時、Google 當機、配額 | D1 說溜了、試算表沒有；寬限時間過了 Cron 會把它蓋成未溜，網站上的紀錄就消失 | K 要決定：(a) D1 為準，Cron 不蓋 `pending` 列，背景重試寫回，重試 N 次仍失敗才標示；(b) 試算表為準（現行 ADR 0007），寫回失敗就回報按的人失敗、不寫 D1。建議 (a)＋在網頁標「還沒寫進試算表」 | 高 |
| 3 | **手動清空欄位** | 有人在試算表把「誰遛的」或「遛狗日期」刪掉 | Cron 要能把 D1 今天的列改成 `walked=0`；若只看「有值的格子」就漏掉（舊研究第 1、2 項同一個問題） | 比對時以「試算表那隻狗今天這兩格的完整值」對 D1，空值也是一種值；清空寫 `walked=0` 而不是刪列，避免觸發器與快取判斷錯 | 高 |
| 4 | **Cron CPU 10 ms** | 每分鐘解析 gviz（約 118 列×多欄 JSON）、比對、組 SQL | 超過就被中止；ADR 0012 第 23 行記錄 Worker 自己同步實測 64–152 ms（那是全量同步） | 只讀主清單需要的欄（gviz `tq=select ...` 縮小回應）、跳過表頭那次讀取（欄位位置快取在 D1）、先比對試算表回應的雜湊，沒變就直接結束。先部署測量版看 `cpuTime`，超過就改每 2–5 分鐘或回到 GitHub Actions | 高 |
| 5 | **日期跨日** | Cron 用 UTC；台灣 00:00＝UTC 16:00；D1 額度 08:00 重置 | 用 `new Date()` 的 UTC 日期就會在 0–8 點把「今天」算成昨天 | 一律用現有 `taiwanYmd(Date.now())`（`worker/src/index.js:977`）；試算表日期也照台灣日解讀。清前一天的 DELETE 放在台灣 00:00 後第一次寫入（現行做法） | 中 |
| 6 | **gviz 快取延遲** | gviz 回應有時落後試算表幾十秒到幾分鐘（推測，沒有官方說明） | 手動改的要多等；更糟的是配合坑 1 把新資料蓋回舊的 | 寬限時間設比 gviz 延遲長；網址加不會影響結果的變動參數（例如 `&_=分鐘數`）降低快取命中（推測，要實測） | 中 |
| 7 | **Cron 數量上限 5 個** | 現在 `wrangler.jsonc:33` 已有 `*/10 * * * *` | 新增 `* * * * *` 要再占一個；帳號下其他 Worker 也共用 5 個 | 合併成一個 `* * * * *`，在程式裡用分鐘數判斷要不要做「每 10 分鐘看要不要叫 GitHub」的事 | 低 |
| 8 | **和 GitHub Actions 同步打架** | 同步把試算表的「遛狗日期」寫進 `v3_sheet_main`／`v3_walks`；Cron 也從同一張試算表寫 `v3_today_walks` | 兩邊讀到不同時間點的試算表，`/api/dogs` 的 `walkedDate` 和今日清單短暫不一致 | 明確分工：今天的狀態只看 `v3_today_walks`；`v3_walks`（歷史）仍由 GitHub 同步寫。前端合併時今天以 `v3_today_walks` 為準 | 中 |
| 9 | **packs 版本觸發器（ADR 0009）** | Cron 若順手更新 `v3_sheet_main_walkers` 等有 `packs_*` 觸發器的表（`db/compact-schema.sql:269-270`） | 每次都讓 small 包版本加 1，所有手機重抓整包狗清單（讀取量暴增） | Cron **只寫 `v3_today_walks`**，不碰有 packs 觸發器的表 | 高（若誤碰）／低（遵守分工） |
| 10 | **觸發器放大寫入** | 每寫一列，`version_v3_today_walks_*` 再寫 1 列；多列 DELETE 每列都觸發 | 寫入大約變 1.5 倍，加索引約 3 倍（見 1-5） | 只寫差異；同一分鐘多筆差異用一個 batch（版本號仍每列加 1，但無妨） | 低 |
| 11 | **索引與讀取量** | 查詢沒走索引就掃全表 | `v3_today_walks` 每天清，全表最多約 260 列，影響小；`v3_walks` 有 `v3_walks_date` 索引（`db/compact-schema.sql:268`） | 新查詢都用 `walk_date=?`；不要對 `v3_walks` 做無條件比對 | 低 |
| 12 | **同時兩支手機按同一隻** | 兩人幾乎同時按溜了 | 後到的覆蓋先到的 `walker`；試算表 Apps Script 是「接在後面」（`docs/PROJECT_GOALS.md:209`），D1 卻是覆蓋 | D1 寫入改成「同一天已有別人就接在後面」，跟 Apps Script 規則一致，或以 Apps Script 回傳的格子內容為準寫回 D1 | 中 |
| 13 | **手機時鐘** | 現行用手機時間比新舊（舊研究第 5 項） | 新架構第 4 點解決：`updated_at` 一律由 Worker 寫 | 前端不再比時間，只看 D1；localStorage 只存「剛按的 dog_key」不參與判斷 | 已解決 |
| 14 | **D1 寫失敗** | 額度用完（ADR 0008 那天）、D1 暫時故障 | 新架構 D1 是唯一來源，D1 寫失敗＝按了沒效果（現行還有試算表接著） | D1 失敗時退回「直接寫試算表」舊路徑並提示；額度預算維持 ADR 0008 的 2 萬列 | 中 |

## 3. 和既有 ADR 的衝突

| ADR | 條文 | 衝突？ | 說明 |
|---|---|---|---|
| 0006 寫入範圍 | 只寫主清單「遛狗日期」「誰遛的」（`docs/adr/0006-sheet-write-scope.md:9-13`） | 不衝突 | 寫回內容不變，只是順序改成先 D1 後試算表 |
| 0007 今日即時 | 「試算表是正本」「Apps Script 寫成功後才記 D1」（`docs/adr/0007-today-walks-live.md:23`、`db/compact-schema.sql:232-234`） | **衝突，要 K 重開** | 新架構今天的狀態以 D1 為準 |
| 0007 | D1 寫失敗不影響按的人（第 17 行） | **衝突** | 新架構 D1 失敗就是按失敗 |
| 0008 寫入預算 | 每天預算 2 萬列、只寫差異 | 不衝突，要補條文 | Cron 寫入要算進預算；Cron 必須只寫差異 |
| 0009 版本包 | 讀取看版本號 | 不衝突 | 沿用 `v3_data_versions.today` |
| 0012 同步 | 「Worker 自己同步、不叫 GitHub」因 CPU 被否決（第 23 行）；「網站寫入不觸發」（第 14 行） | **部分衝突，要 K 確認** | Cron 每分鐘只讀今天兩欄，不是全量同步；但仍是 Worker 讀試算表寫 D1，與當初否決理由同類，要用實測 CPU 說服 |

## 4. 建議實作順序

1. **CPU 實測**（不改行為）：在現有 `*/10` Cron 裡加一段「讀主清單兩欄、算差異、只記日誌不寫」，看 Cloudflare 日誌的 CPU 時間。超過 10 ms 就停在這步，回頭考慮每 5 分鐘或保留 GitHub。
2. **D1 結構**：`v3_today_walks` 加 `pending`、`written_at`（寫進 `db/compact-schema.sql`）；確認不新增 packs 觸發器。
3. **按溜了改成先寫 D1**：Worker 寫 D1（`pending=1`、伺服器時間），再叫 Apps Script，成功改 `pending=0`；失敗保留並重試。
4. **Cron 每分鐘比對**：跳過 `pending` 與寬限期內的列；空值也比；只寫差異；沒差異不寫任何列。
5. **前端**：拿掉 `/walkers` 輪詢對今日狀態的影響與手機時鐘比對，只看 `/api/today`；localStorage 只記「剛按的先別移位」。
6. **改 ADR 0007／0012**，補 0008 預算條文；PR 附寫入量預估。

## 5. 需要 K 決定的事

1. 今天的溜狗狀態改成「D1 為準、試算表是副本」（推翻 ADR 0007 的「試算表是正本」）可以嗎？
2. 寫回試算表失敗時：D1 保留並重試（網頁標「還沒寫進試算表」），還是整個按溜了算失敗？
3. Cron 頻率：每分鐘（要通過 CPU 實測），還是可接受每 2–5 分鐘？只在台灣 7–22 點跑可以嗎？
4. 寬限時間：網站剛寫的列幾分鐘內不讓試算表蓋掉（建議 3–5 分鐘）？
5. 同一隻狗兩人同時按：D1 也「接在後面」，還是後按的蓋掉？
