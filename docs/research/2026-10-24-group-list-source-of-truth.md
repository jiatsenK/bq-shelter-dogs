# 常遛狗群名單以誰為準：試算表直接改怎麼辦

研究日期：2026-10-24（台灣時間）。Agent：Claude。唯讀研究：沒有改程式、沒有部署、沒有觸發 workflow、沒有打網站 `/api`、沒有寫 D1；只用 `wrangler d1 execute --remote` 下兩次 SELECT（`rows_written: 0`）。行號以分支 `claude/retro-issue-closeout`（main `2a05e25` 之後）的工作樹為準。

背景：#538 的終點是「D1 唯一正本、試算表只剩輸入」；#538「還差」把「狗群頁仍先寫試算表」掛在 #474 底下，#474 的完成條件沒有涵蓋，等 K 決定。K 的疑問：志工習慣直接在試算表改狗群，如果狗群頁改成 D1 為準，試算表直接改怎麼辦？

> **K 決定（2026-10-24）**：不採下方建議的 C1，改採 **C2**：網站的常溜狗群頁只能看，加狗、移出、開新群三個都拿掉；Worker 的狗群寫入和 Apps Script 的 `group` 動作一起刪（避免誤用）；試算表直接改不另記編輯紀錄。實作見 #474；整欄插入／刪除實測另開 #550。以下保留研究當時的內容。

## 結論

1. **試算表直接改，現在就已經會進 D1，而且幾秒內就到。** GAS 編輯觸發把改到的那幾欄記成 `groups:欄`，馬上送整欄名單給 Worker，Worker 整欄比對、有變才換（`apps-script/sheet-write.gs:426-449`、`:697-701`；`worker/src/dog-list.js:187-207`）。送不出去每 10 分鐘補送，每天三次保險掃描比指紋，**狗群也在掃描範圍內**（`sheet-write.gs:682-694`）。換句話說，狗群跟主清單一樣，已經是「試算表輸入、GAS 推給 D1、網站讀 D1」。
2. **唯一還「先寫表」的是網站狗群頁的加狗／移出／開新群**（`worker/src/index.js:976-1017`）。這個寫法是「對試算表做一次增減」（GAS 在鎖裡讀現值再加一隻或拿掉一隻，`sheet-write.gs:41`、`:356-402`），**不會蓋掉別人在表上的改動**；D1 整欄換成 GAS 回的結果。現況有一個很少見的漏洞：網站寫完、人工緊接著改同一群時，D1 可能被較舊的名單蓋回，而且指紋已經對上，保險掃描補不回來（見第 2 節）。
3. **實際使用量非常少。** 正式 D1 編輯紀錄（從 2026-10-17 起共 65 筆）只有 **1 筆** `kind='group'`（2026-10-23）。人工改表的次數**查不到**：`applyGroup` 不記編輯紀錄，GAS 執行紀錄不在 repo 能讀的範圍。
4. **建議採選項 C1：維持網站先寫試算表，補上漏洞，再把「狗群名單＝試算表輸入、D1 是網站讀的正本」寫成文件**，把狗群歸到跟主清單同一類，視為已達 #538 的意思。比照今日溜狗（選項 B）要補一整套寫回佇列、穩定的群 ID、三方比對，規模接近今日溜狗的一半，換來的只是「試算表掛掉時網站還能改狗群」，以目前一週一次的用量不划算。
5. **要 K 決定**：#538 的「網站操作先寫 D1」要不要把狗群當例外（或把網站改狗群收掉）；見最後一節。

## 1. 現況：試算表直接改常遛狗群，怎麼進 D1

### 觸發時機

- `installWalkEditTriggers` 建安裝型「編輯時」→ `onWalkSheetEdit`、每 10 分鐘 → `flushDogList`、每天 09:43／13:53／23:53 → `dogListScan`（`apps-script/sheet-write.gs:414-424`）。
- `onWalkSheetEdit` 看分頁名是「常遛狗群」就當 `kind='groups'`（`:430`），由 `dogListKeysForEdit` 把**改到的每一欄**記成 `groups:<欄>`（`:697-701`），寫進指令碼屬性 `DOG_LIST_PENDING`（`:436-440`），然後**立刻** `flushDogList()`（`:449`）。狗群不走今日溜狗那條（`:441` 排除 `groups`）。
- 網站經 GAS `doPost` 寫的是程式寫入，**不會**觸發編輯觸發器（`:407` 註解）。

### 送什麼

- `flushDogList` 送出當下**重新讀整個分頁**（`dogListSheets`，`:552-556`），用 `dogListUnits` 算出那一欄的 `{ sheet:'groups', column, names, label, hash }`（`:682-694`），每批最多 10 個單位（`:547`）。所以送的是**送出那一刻的整欄**，不是編輯當下的值，也不是差異。
- 讀表與送出都拿 script lock（`:571-583`），跟網站寫表（`handleRequest` 的 `lock.waitLock(15000)`，`:41`）是同一把，所以讀到的不會夾在網站寫一半的中間。
- Worker 端 `applyGroup`（`worker/src/dog-list.js:187-207`）：名字只留主清單上有的、用主清單寫法、去重、去純數字；群名是數字或狗名就當空的。跟 D1 那欄一樣就不寫（`:198`），不一樣就**整欄刪掉重插**；群名另比。**不記編輯紀錄**（整個 `applyGroup` 沒有 `logEdit`）。
- 群的身分是**欄位編號**（`v3_sheet_groups.column_index`，`db/compact-schema.sql:162-172`）。

### 失敗怎麼補

- `walkWorker` 丟錯或 Worker 沒 `ack` 就留在 `DOG_LIST_PENDING`，每 10 分鐘 `flushDogList` 再送（`sheet-write.gs:580-586`）；Worker 只有 D1 失敗才回 `ack:false`（`dog-list.js:236-239`）。
- **保險掃描包含狗群。** `dogListScan`（`sheet-write.gs:600-617`）把 `dogListUnits` 的所有單位指紋送出，其中就有每一欄 `groups:<欄>`（`:682-694`）；Worker `scanDogList` 回指紋不同的（`dog-list.js:255`），GAS 依 `main → departed → groups → notes` 的順序補送（`sheet-write.gs:620-623`，狗群要用主清單的犬名對）。
- 指紋存在 `v3_sync_state` 的 `dog_list_fp`，只在 `applyDogListRows` 收到該單位時更新（`dog-list.js:234`）。**網站 `replaceGroup` 不更新指紋**（`worker/src/compact.js:127-137`）。

### 沒驗證的

- 「常遛狗群」分頁**插入／刪除整欄**有沒有觸發、範圍是什麼：主清單實測沒做到這項（研究 2026-10-23 表格只有列操作）。因為群以欄位編號當身分，插一欄會讓右邊所有群在試算表上位移；若觸發器只送插入那一欄，D1 會到下次保險掃描（最長約 10 小時）才全部對齊。這段時間網站送 `column=N` 給 GAS，GAS 會改到位移後的那一群（`sheet-write.gs:379-380` 直接用 `req.column`）。

## 2. 網站寫入與人工改表交錯時會怎樣

網站狗群頁：`public/js/group-stage.js:209-236` → `POST /api/groups` → `writeGroup`（`worker/src/index.js:976-1017`）：先 `callSheet` 叫 GAS（`:1002-1006`），GAS 在 script lock 裡讀現值、算出「加一隻／拿一隻／開新欄」寫進表（`sheet-write.gs:162-176`、`:356-402`），回這一欄寫完後的整欄名單；Worker 再用 `replaceGroup` 整欄換 D1（`index.js:1011`），寫一筆 `kind='group'` 編輯紀錄（`:1013-1015`）。

| 情境 | 現在的結果 |
|---|---|
| 人工先改 A 群、網站後加狗到 A 群 | GAS 在鎖裡讀到人工改過的值再加一隻，表上兩邊都留住；D1 換成包含兩邊的名單。**正確。** |
| 網站加狗、之後人工改 A 群（間隔幾秒以上） | 網站的 `replaceGroup` 先到 D1；人工的 `flushDogList` 讀到兩邊都有的整欄送來，`applyGroup` 換掉。**正確。** |
| 網站剛寫完表、人工在 GAS 回應到 Worker `replaceGroup` 之間又改了 A 群，而人工那次 `flushDogList` 比 `replaceGroup` 先到 D1 | D1 先變成「含人工」的版本、`dog_list_fp` 記成最新表的指紋，接著 `replaceGroup` 把 D1 蓋回「不含人工」的版本。表與指紋一致，**保險掃描不會再要這一欄**，D1 錯到下次有人改這一欄為止。發生條件是兩個請求在數百毫秒內反序，**很少見，但補不回來**。 |
| GAS 寫成功但 Worker 等回應逾時（`worker/src/sheet-write.js:34-38`） | 網站顯示失敗、D1 沒換；表已改、指紋還是舊的，下次保險掃描補回；志工重按會得到「本來就在這一群」並把 D1 換對。 |
| 試算表或 GAS 掛掉 | 網站改不了狗群（`index.js:1002-1006` `sheetFail` 回錯）；人工改表留在 `DOG_LIST_PENDING`，恢復後補送。 |

「以欄位為單位整欄覆蓋」的影響：

- **試算表上沒有整欄覆蓋**：網站對表只做增減，所以不會蓋掉人工的改動。整欄覆蓋只發生在 D1，而 D1 兩條路（`replaceGroup`、`applyGroup`）的內容都是**某一刻的表**，所以正常情況會收斂到表；唯一例外就是上表第三列的反序。
- 一欄只有幾隻狗（正式 D1 11 欄共 65 格，平均 6 隻），整欄重寫的寫入量很小；#474 要補的是證明它跟其他群、主清單大小無關的讀寫量測試。
- 人工改表**沒有編輯紀錄**，網站的編輯紀錄頁只看得到網站改的；誰在表上拿掉哪隻狗，網站查不到。

## 3. 選項比較

使用頻率（正式 D1，唯讀）：網站改狗群從 2026-10-17 有編輯紀錄以來只有 1 次（全部 65 筆裡，撤銷溜了 26、固定照顧 15、照片 10）。人工改表次數查不到（理由見結論 3）。

| | A 維持現狀 | B 比照今日溜狗 | C1 維持先寫表＋補漏洞（建議） | C2 網站不改狗群 |
|---|---|---|---|---|
| 做法 | 網站先寫表，成功後 `replaceGroup` 換 D1 | 網站先寫 D1，背景用加／減操作寫回表；人工改表照舊整欄送 D1，以最後出現為準 | 同 A，另外：`replaceGroup` 時讓那一欄的指紋失效（或帶寫表當下的指紋），保險掃描一定會再對一次；人工改表也記編輯紀錄（系統代記） | 狗群頁只看不改，改狗群一律在試算表 |
| 志工體驗 | 跟現在一樣；表掛掉時網站不能改 | 表掛掉時網站照樣能改，畫面立刻變；之後表才跟上 | 跟現在一樣 | 少一個入口；現場要改得找能編表的人（志工本來就沒有表的編輯權，`PROJECT_GOALS.md` 資料源一） |
| 衝突規則 | 表上增減不互蓋；D1 有反序漏洞 | 網站寫回前人工整欄送到，會把網站剛加的狗從 D1 蓋掉，等寫回表後下次掃描才回來；要避免就得做「上次同步基準」三方比對（比照 `v3_walk_baselines`） | 表上增減不互蓋；反序漏洞最晚在下次保險掃描補回 | 只有一個輸入點，沒有衝突 |
| 要改的範圍 | 無 | 新寫回佇列表＋重試（接 Worker cron 的寫回重試）、每欄基準與三方比對、穩定的群 ID（現在用欄位編號，表上插欄就對錯群）、「開新群」寫回要有請求 ID 才不會重試時開兩欄、GAS 端回執、前端改讀 D1 回應、測試；參考規模：今日溜狗的 `worker/src/walk-accept.js` 449 行＋`walk-reconcile.js` 75 行，狗群較單純但仍是同一套機制 | `worker/src/compact.js` `replaceGroup` 或 `index.js` `writeGroup` 幾行、`dog-list.js` `applyGroup` 加 `logEdit`、對應測試；可和 #474 同一張 PR | 前端拿掉加狗／移出／開新群（`group-stage.js`）、Worker 停用 `/groups`（或回 410）、GAS 可拿掉 `writeGroup`、ADR 0006 改寫 |
| 風險 | 反序漏洞補不回 | 規模大、新增一條寫回路徑；欄位編號當 ID 的問題在 B 會從「偶發」變成「寫錯群」 | 低；只是修補 | 拿掉的是 K 2026-10-16 開放的功能，要 K 點頭 |
| 跟 ADR 0018／#538 一致性 | 不一致（網站操作沒有先寫 D1），#538 那格永遠勾不了 | 最一致 | 「試算表輸入、D1 是網站讀的正本」跟主清單一致；但「網站操作先寫 D1」要把狗群列為明文例外 | 一致（沒有網站操作，試算表只剩輸入） |

補充：選項 B 的「以最後出現為準」不能直接沿用 ADR 0018 第 4 點。今日溜狗是一隻狗一格，最後一筆就是答案；狗群是一欄多隻，人工送來的是整欄，網站送的是增減，兩種粒度混在一起，沒有基準就會互相吃掉。

## 4. 建議與要 K 決定的事

**建議：C1。** 理由：

- 試算表直接改已經走「GAS 編輯觸發 → D1」，跟主清單完全同一條路；K 擔心的「大家在表上改怎麼辦」現在就有答案，不需要因為網站改法而改變。
- 網站對表只做增減、在鎖裡讀現值，所以「先寫表」反而讓人工與網站不互蓋。改成 D1 先寫（B）會失去這個性質，要多做三方比對才補得回來。
- 用量一週一次，B 唯一多給的是「表掛掉時網站能改狗群」。
- 反序漏洞和「人工改表沒有編輯紀錄」用幾行就能補，可以跟 #474（`mainNameMatcher`、讀寫量測試）同一張 PR。

要 K 決定：

1. #538「網站操作先寫 D1」要不要明文把狗群頁列為例外（C1）？還是改走 B，或乾脆收掉網站改狗群（C2）？
2. 若選 C1：#538 那格要寫成「狗群：試算表輸入、D1 正本，網站狗群編輯維持先寫表（例外，理由見本研究）」後勾掉，還是留著等以後？
3. 人工改表要不要記進編輯紀錄？編輯者寫成「試算表」之類的系統名（拿不到是誰改的：GAS 安裝型觸發器的 `e.user` 依帳號權限不一定拿得到，本研究沒驗證）。
4. 要不要在測試試算表實測「常遛狗群」插入／刪除整欄、拖曳整欄時觸發器送什麼？群以欄位編號當身分，這項不管選哪個都會影響；選 B 前一定要先做。
5. `docs/PROJECT_GOALS.md:222` 還寫「同籠關係的唯一真相來源」是試算表，要依決定改寫。
