# #460 試算表和網站之間，真的需要四件工作嗎？

- 日期：2026-10-22（台灣時間）。Agent：Claude Code 背景研究代理。
- 問題：K 問「有需要這麼多嗎」。目前有四件工作：①試算表同步、②改表通知比對（#458）、③保險掃描（#459）、④派送寫回（#460）。能不能合併？
- 範圍：只讀程式（`claude/460-d1-unified` 分支）、`docs/design/456～460`、ADR 0017 與 #441 規格（`git show 444c33e:…`）、既有研究。沒改程式、沒部署、沒線上測試。

## 結論

- **四件裡，真正獨立的只有兩件：「把狗清單抄到網站」（①）和「今日溜狗的雙向對帳」（②③④）。** ②③④其實是同一件事的三個入口，可以收成一個程式路徑。
- **④ 已經是「按下去當場寫」**：`/api/walk` 接受後馬上在背景派送（`worker/src/index.js:947` 的 `ctx.waitUntil(dispatchWalk…)`）。Cron 裡的④只是補失敗、補沒送成的。不需要再改成「點的時候寫」。
- **② 和 ③ 讀的是同一份東西**：Apps Script 的 `walkCompare` 和 `walkScan` 都先呼叫同一個 `readWalkSnapshot(sheet)` 讀整張主清單四欄（`apps-script/sheet-write.gs`）。差別只在比對放在 Apps Script 還是 Worker。可以改成「通知＝馬上跑一次保險掃描」，少一套程式。
- **③ 不能直接併進 ①**：①是叫 GitHub Actions 用 gviz 讀表（`scripts/sync-sheet.mjs:31`），規格明文規定「僅 gviz 舊讀取不算可信人工修正證據」。要併，得讓①改用 Apps Script 直接讀，這是大改，不建議。
- **最少可以變成「一個 Cron 時段，兩件事」**：①照舊；②③④合成「溜狗對帳」一個入口。信心：中高（程式結構確定；合併後 CPU 仍要量）。

## 1. 四件工作現況

| | 做什麼 | 怎麼觸發 | 讀表方式 | 碰的欄位 |
|---|---|---|---|---|
| ① 試算表同步 `syncTick` | 狗清單、照片等抄到網站 | Cron 每 10 分鐘；有改才叫 GitHub Actions（`index.js:550`、`triggerSync`） | gviz | 全部，含「遛狗日期」「誰遛的」（`sync-sheet.mjs:76、107`） |
| ② 改表通知比對 | 人工改表後馬上收進 D1 | Apps Script 變更觸發器 → `POST /api/sheet-changed` → `compareNotifiedWalks` | Apps Script 直接讀（`walkCompare`） | 編號、狗名、日期、名單 |
| ③ 保險掃描 `scanWalks` | 補漏掉的通知 | Cron（剛決定改每 10 分鐘），在 `retryWalks` 裡 | Apps Script 直接讀（`walkScan`） | 同上 |
| ④ 派送 `dispatchWalk` | D1 接受的溜狗寫回試算表 | 按下去當場背景送；Cron 補失敗（`walk-retry.js`） | Apps Script 鎖內讀＋寫 | 日期、名單 |

`scheduled()`（`index.js:1271` 起）同一次 Cron 同時跑 ①和 `retryWalks`（②的補跑＋③＋④補送）。

## 2. 逐題回答

### ③ 能不能併進 ①？

不能直接併。原因寫在規格與 ADR：

- 規格：「僅 gviz 舊讀取不算可信人工修正證據。」
- ADR 0017 第 3 點：「未確認期間，gviz 舊快照不能撤銷 D1 新操作；直接讀值／寫入回執與後續讀回才能推進一致基準。」
- ADR 0017 第 7 點：「舊同步不能再用試算表舊快照覆蓋這些欄位。」

gviz 為什麼不可信：Google 沒公開 gviz 的快取時間，社群回報有幾十秒到幾分鐘的延遲（`docs/research/2026-10-20-sync-pitfalls.md` 第 10 條，標「推測」）。網站剛寫進表的名字，gviz 可能還讀到舊的，會被誤判成「有人手動刪掉」。

要併只有一條路：把①改成也用 Apps Script 直接讀。但①跑在 GitHub Actions、讀全部欄位、還要處理照片和歷史，改動面很大，也會吃 Apps Script 配額。省下的只是一次 Apps Script 呼叫，不划算。**另一個方向倒是可行：①已經讀到溜狗欄位，只是不准拿來當證據；那就維持「①不碰溜狗欄位」，責任分清楚即可。**

### ② 和 ③ 能不能共用？

可以，而且幾乎是現成的：

- 兩者在 Apps Script 端都先 `readWalkSnapshot(sheet)` 讀整張主清單四欄，讀表成本一樣，沒有「逐狗讀比較省」的差別（規格也要求「不逐狗發出遠端請求」）。
- 差別：`walkCompare` 帶著 Worker 的已知基準去 Apps Script 比、一次最多回 5 筆差異；`walkScan` 把整份讀回 Worker 自己比（`reconcileWalkSnapshot`）。
- 合併做法：通知進來時只做「記有改＋馬上跑一次 `scanWalks`」，刪掉 `walk-notify.js` 和 `walkCompare`。
- 代價：通知那一次要把整份四欄（約 200～500 列）傳回 Worker，回傳量比較大；Worker 端比對 CPU 在本機量過只有 P99 0.4～0.9 ms（`docs/design/460-d1-walk-unified.md:85`），影響小。重送合併、失敗補跑的邏輯要搬到掃描這邊。
- 這是實作選擇，不違反 ADR：規格只要求「收到通知立即啟動必要欄位比對」「Cron 補漏」，沒有規定兩條要分開寫。

### ④ 能不能改成按下去當場寫，Cron 只補失敗？

已經是這樣。`/api/walk` 先存 D1、回覆手機，再用 `waitUntil` 背景派送；Cron 只撿 `pending／retry／unconfirmed` 到期的和中斷的。ADR 0017 鎖定的是「D1 接受就算成功、試算表背景寫回」：「網站操作先可靠存入 D1，再背景寫回」「D1 已接受的操作不因寫回失敗退回」。所以「等試算表寫完才回成功」（舊流程）是**鎖定不能回去的**；但「當場背景送＋Cron 補」本來就是現況。

## 4. 最少工作的設計

**「兩件事」版本：**

1. 試算表同步（①）：照舊，每 10 分鐘有改才叫 GitHub，不碰今日溜狗欄位。
2. 溜狗對帳（②③④合一）：一個函式「讀一次四欄快照 → 收人工修改 → 把待寫回的一次送出」。三個入口都呼叫它：按下去（只送這隻）、改表通知（馬上跑）、Cron 每 10 分鐘（補漏＋補送）。

好處：少一套比對程式（`walk-notify.js`、`walkCompare`）、Apps Script 端少一個動作、要測的路徑變少，K 比較好理解。
壞處：通知那次回傳整份四欄，資料量變大；要改已寫好的 #458 程式和測試；合併後同一輪工作變重，CPU 仍要再量（目前 Cron 只剩不到 2 ms 空間，見 `docs/design/460-d1-walk-unified.md:114`）。

**不需要 K 重開鎖定就能做**：上面的合併都在規格允許範圍內。

**要 K 重開鎖定才能做的更極端版本**：

- 拿掉③（只靠通知）：Apps Script 安裝型觸發器官方沒有保證每次都送達，且有每日觸發器總執行時間配額；拿掉要 K 同意「通知漏掉就等明早 6:30 同步」，而且那份同步是 gviz，又違反「gviz 不算證據」。不建議。
- 拿掉②（只靠每 10 分鐘掃描）：要 K 接受「手改表最慢 10 分鐘網站才變」。ADR 0017 第 5 點寫「通知立即比對」，要重開。
- ①③合一用 gviz：要推翻「gviz 不算證據」，有誤刪網站剛登記名字的風險。不建議。
