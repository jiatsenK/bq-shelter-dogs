# #441 今日清單版本快取與帳號預算驗證

日期：2026-10-21（台灣時間）。Agent：CODEX。

結論：**資料正確性與快取失效測試通過；200 列壓測的 CPU／最壞讀取量不能視為已通過免費方案門檻。** 現有讀取方法確實省讀取，但整天都是 miss 時，僅手機輪詢即超過免費讀取額度；CPU 的最大分組 P99 也量到 10.591 ms。這不是正式功能實作或部署。

## 方法與版本

- 同一分支 `prototype/d1-walk-sync`，比較基準 `81285be`。只啟用同一專屬測試 Worker，測試版本 `f32a23ba-7a42-4ddb-b4b2-c39121240f36`，測試 D1 `9e23a65c-c9dd-4f83-ad9c-2e01626910f0`。
- **直接匯入、未修改** `worker/src/today.js` 的 `readTodayWalks`，已確認與本次查得的遠端 main `2ebe74c` 相同。來源 LF SHA-256：`4ee957c776fe0ca015d94f3647607006865dd404814a51772dbffbef2470a8a8`。
- SQL adapter 僅允許原函式的兩個 SELECT，改指向 `bench441_cache_versions`／`bench441_cache_today`；主鍵、欄位與三種版本觸發器仿照原 schema。保留 adapter 身分，使原函式的 `cache.db === db` 條件有效。
- 用 AsyncLocalStorage 分開計量每個請求，避免 30 個並行請求互相污染讀取數。版本查詢的 `.first` 以 `.all` 取得同一 SQL 的 D1 metadata，再取第一列的 today；這是量測包裝成本，不修改正式讀取邏輯。
- 測試資料為 **200 筆假狗列**，其中一列用測試複本的狗編號 `2024010501`，其餘 199 列為 BENCH 假資料。200 是壓測規模，**不是聲稱正式今天有 200 隻狗**；前一輪複本比對只有 116 隻。
- 200 筆 fixture 分兩次各 100 個 INSERT，實際各寫 300 列（包含主鍵與版本觸發器）；schema 另讀 3／寫 9。建立前帳號查得當日已寫 391 列，保守預留本次 1,500 列，仍低於 ADR 0008 的 20,000 列預算，單批也低於 500 列。
- 沒有正式資料讀寫、正式 schema 變更、正式部署或新的排程。既有測試 pending 表與前輪紀錄保留。

原始可重算證據：[cache evidence](2026-10-21-d1-walk-cache-evidence.json)。含每次請求 D1 metadata、選取 CPU 事件、帳號聚合用量、schema metadata 及 Google 測試格清空／還原時間。排除金鑰、IP、request headers、原有志工姓名。

## 直接改試算表的驗證界線

- 先用連接器讀 metadata 及 B9:E9 的有效值、公式、驗證與格式，確認是 BENCH441 複本、宙斯編號正確，E9 只有測試名字、無公式或驗證限制。
- 只暫時清空 `主清單!E9` 的 userEnteredValue；呼叫測試 `/cache/notify`，由 Worker 重新讀 gviz 的該狗列並投影到測試 today 表，觸發版本更新，30 位讀者全部看到空名單。
- 還原前再次讀取並確認 E9 仍空白，避免覆蓋別人的修改。只恢復先前 32 個測試名字的值；再通知並驗證 30 位讀者看到完整名單。最後連接器確認值與原備份完全一致、userEnteredFormat 未變。
- 這是 **API 直接編輯複本＋明確 HTTP 通知** 的可重現測試，不是瀏覽器人工操作，也沒有測 Apps Script 觸發器到 Worker 的整段連線。K 前一輪回報三項人工操作都有事件，原始事件細節仍未取得。
- 此 projection 只處理測試狗今天的名字；沒有投影 D 欄日期，不能宣稱「改日期」已驗證；沒有 pending 與手動刪名衝突、三方合併或撤銷語意。
- 兩次第一次 gviz 投影就讀到預期內容，但 API 修改與通知間有工具調度空檔，不能將這個空檔當作 gviz 固有延遲，或據以決定寬限期。

## CPU 與觀測限制

台灣時間約 10:28–10:33 執行此輪讀寫。tail 共捕獲測試版本 185 筆事件，CPU 0–10 ms、outcome 全為 ok。捕獲並非完整事件全集，沒有替未捕獲請求填 CPU；客戶端本輪成功也不代表所有未來情況都不會超時。

量測包括 HMAC 驗證與 ALS 包裝；不將強制 reset 的資料快取 miss 等同新的平台 isolate。此輪第一次 GraphQL 補查遇到 rate-limit budget 錯誤，證據保留原錯誤，不將缺值當零或拿前一輪 CPU 代替。超過 API 指示的 5 分鐘後，以較窄時段與較小筆數上限補查一次成功：28 組、215 次請求，最大組 P99 **10,591 微秒＝10.591 ms**，已高於 10 ms。這是分組分位數，不是逐次最大值；tail 整數精度的 10 ms 不能用來宣稱所有 CPU 都不超標。

**沒有足夠證據宣稱完整正式管線有 CPU 餘裕。** 官方說明允許偶發 CPU 超限有彈性，所以本次 HTTP 成功及 outcome=ok 並不矛盾；不能把這種彈性當成穩定符合免費方案門檻。正式管線上線前仍須減少工作量並重新驗證。

## 用實測成本推算全天（全段皆為條件推估）

假設 30 人、每天 15 小時、每分鐘一次，為 **27,000 次手機請求／日**。以下不是整天實測，也不是保證命中率。

| 情境 | 手機輪詢 D1 列／日 |
|---|---:|
| 全部命中，只讀版本號 | 27,000 |
| 使用本次第 1、2 分鐘平均，每次 51 列 | 1,377,000 |
| 200 列 fixture，每次均 miss（已單次量測 201 列） | 5,427,000 |
| 假設名單只有 116 列，且每次都 miss（117 列成本為依 schema 的推算，非本輪另測） | 3,159,000 |

前輪實測的一致比較每次讀 116 列；若每分鐘一天為 167,040 列。假設 pending 表一天掃 200 列、每分鐘一次，再加 288,000 列；這是刻意把 pending 累積列數列出的假設，**不是目前只有 12 列的實測狀態**，正式保留策略還未敲定。

例：`1,377,000 + 167,040 + 288,000 + 126,930 = 1,958,970` 列／日，低於免費 500 萬，尚餘 3,041,030 列供其他新增操作。但這仍沒計入登記、通知、重新整理等額外讀取，且使用的是短時段命中率與近期基線，不是無條件上界。若改加七日最高基線，則為 `5,420,736` 列，已超過免費讀取額度。200 列全 miss 更是只算手機就超標。

用同一個每分鐘 Cron 假設，單輪詢＋Cron 是 `27,000 + 1,440 = 28,440` 請求；加七日最高帳號基線 6,905 為 35,345，尚須加登記、通知及重試入口，不能漏算。單次登記已測總寫 5 列、直接 Sheet 投影已測寫 2 列；一天登記／手改次數尚未量到，必須保留 ADR 0008 的實際帳號預算檢查，不把未測次數寫成事實。

## 判定與下一步

1. **已證實**：版本號快取可用；登記、清空、還原都能讓其他讀者失效重讀，沒有因快取而永久保留舊名字。三個情境的 180 次讀取均驗證完整 200 列。
2. **未通過壓測門檻**：200 列全 miss 的讀取量反例已存在，CPU 最大分組 P99 10.591 ms 亦超過 10 ms；不能宣稱任意分流、資料量與帳號異常日都維持免費。量測含包裝成本，亦不能直接斷言正式版本必然有同樣 CPU。
3. **可帶入 ADR 的決策**：依目前複本 116 隻與可接受的最壞名單量，決定 Cron 頻率、帳號預算與超預算時保留 pending 的行為；若必須涵蓋 200 列且不依賴記憶體命中，就要再驗證能限制冷讀成本的資料包方案。這是候選方向，不是擅自更改已確認架構或替 K 定案。
4. 此輪已停止即時 tail，測試服務以到期版本 `35dec6c5-ebff-4818-8a5d-bed442137144` 停用、正確金鑰請求回 410；沒有新增 Cron。測試格還原，保留新增的測試登記與 D1 假資料供核對。

Node 全套 346、網頁 261 及附加互動測試通過，原型語法與打包檢查通過。正式環境尚未實作或部署；#441 不關票，不以本報告宣稱所有完成標準已滿足。
