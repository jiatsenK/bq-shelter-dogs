- `migrations/0021_sheet_stays.sql`、`db/compact-schema.sql`：新表 `v3_sheet_stays`（犬名原文當 key、dog_id、籠位、備註、`missing_at`）與 3 個 `packs_` 觸發器（改了讓在所資料包重算）。同一個 migration 做上線轉換：主清單複本上符合暫住判斷的沒編號列轉成暫住紀錄（候選時間照搬）、移出主清單複本；符合判斷、沒有其他資料掛在身上的假狗刪掉，有資料的留著待核對。
- `worker/src/dog-list.js`：`stayTarget` 判斷暫住列、`applyStay` 寫暫住紀錄（新的記「暫住開始」，改籠位或備註只更新）；`readMain` 同一個 batch 讀主清單複本與暫住紀錄；`reconcileMissing` 讓暫住紀錄照同一套候選規則，確認時刪掉暫住紀錄、記「暫住結束」（修改紀錄排在 DELETE 前、用同一個條件），回傳改成 `{ candidates, confirmed }`。
- `worker/src/compact.js`：在所資料包把暫住紀錄當成沒編號的一列接在狗清單後面送出（欄位同以前的假狗，少了 `dogId`），志工網站程式不改。

## 例外與要注意的

- 已經是暫住紀錄的列，那隻狗之後離開主清單也照舊當暫住（不然同一個 key 會變成暫住紀錄加一隻新狗兩份）。反過來，轉換前就建成狗、還在主清單複本上的舊暫住列照一般列處理。
- 暫住列不看溜狗欄：溜狗寫回照編號寫那隻狗本來的列。
- 擁有者要做：先跑 D1 migration（`0021`），**套完馬上部署志工 Worker**。中間如果有人改到暫住列，舊程式會再建一隻假狗，新程式上線後那隻會跟暫住紀錄同時送出，要等那一列消失才會確認掉。Apps Script 不用重新部署。
